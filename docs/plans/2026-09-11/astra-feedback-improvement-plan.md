## 1. 기획 결론

감사 문서의 디자인·콘텐츠 10개, 사용 경험 13개, 개발 18개, 운영·AI 품질 7개 등 **총 48개 항목을 모두 수용한다.** 다만 모든 항목을 같은 방식으로 즉시 구현하지는 않는다.

- 재현된 장애와 데이터 유실 위험은 즉시 수정한다.
- 사용성·접근성 문제는 핵심 동선을 기준으로 다음 배포에 포함한다.
- 콘텐츠 개선은 검증 가능한 자료가 준비된 대표 사례부터 적용한다.
- 조건부 위험과 확장 제안은 정책 또는 측정 기준을 먼저 확정한 뒤 구현한다.
- 이미 구현된 보안·미디어·테마·RAG 기반은 제거하거나 중복 구현하지 않고 회귀 방지 대상으로 유지한다.

가장 중요한 제품 원칙은 **“빈 콘텐츠처럼 보이는 장애를 없애고, 작성한 데이터를 잃지 않으며, 방문자가 실제 역량의 근거에 빠르게 도달하게 한다”**이다. 따라서 대규모 시각 개편보다 조회 신뢰성, CMS 데이터 보존, 접근성, 출시 판정의 정확성을 먼저 복구한다.

## 2. 목표와 성공 상태

### 2.1 목표

1. 발행된 콘텐츠가 홈·목록·상세·RSS·사이트맵에서 동일하게 조회된다.
2. CMS 저장 실패나 상태 전환 이후에도 작성 데이터와 실제 발행 상태가 보존된다.
3. 320px 화면, 키보드, 두 테마에서 핵심 탐색·문의·챗봇 동선을 완료할 수 있다.
4. 홈과 대표 프로젝트가 역할, 기여, 결과, 근거를 30초 안에 전달한다.
5. 테스트·readiness·RAG 평가가 실제 사용자 장애와 품질 실패를 출시 전에 차단한다.
6. 콘텐츠와 트래픽이 늘어날 때 조회·미디어·운영 비용을 측정하고 확장할 수 있다.

### 2.2 최종 성공 기준

| 영역 | 성공 기준 |
| --- | --- |
| 공개 콘텐츠 | 테스트 DB의 발행 글 수와 홈·블로그·RSS·사이트맵 결과가 일치하고, 대표 상세 URL이 200을 반환한다. |
| CMS | 검증 실패·중복·충돌·일시 오류 뒤에도 모든 입력이 남고, 즉시 발행 후 일반 저장이 발행 상태를 되돌리지 않는다. |
| 접근성 | 320·360·390px, 200% 확대, 키보드 전용, 라이트·다크 테마에서 핵심 동선이 완료되고 목표 대비를 충족한다. |
| 콘텐츠 | 대표 사례마다 개인 기여, 설계 이유, 검증 결과, 한계, 증빙 또는 공개 제한 사유가 있다. |
| RAG | 낮은 전체 성공률, 필수 답변 조건 실패, 지연 초과, 평가 case 누락 중 하나라도 있으면 release gate가 실패한다. |
| 운영 | dependency readiness와 제품 smoke를 구분하고, 배포 후 대표 콘텐츠와 챗봇 출처 URL을 자동 확인한다. |

## 3. 범위와 의사결정

### 3.1 이번 계획에 포함

- Supabase 관계 조회 명시, 오류 전파 및 캐시 정책 재설계
- CMS 전체 폼 상태·임시 저장·발행 상태 동기화
- 전역 CSS 계층, 대비, 반응형, 문서 구조, 카드·메뉴·문의 동선
- 챗봇 dialog·상태·긴 대화·부분 답변 경험
- 홈·소개·프로젝트·블로그의 정보 구조와 검증 가능한 콘텐츠 보강
- 실제 DB 계약·프로덕션 서버·접근성·RAG release gate 회귀 검사
- 데이터 타입, Markdown/RAG 구조, 성능 기준선, 운영 복구와 재현성 고도화

### 3.2 정책을 먼저 확정하는 항목

- **미디어 공개 범위(E11):** 현재 포트폴리오용 미디어는 공개 자료로 취급한다. CMS에 민감 자료 업로드 금지 안내를 추가한다. 비공개 첨부 요구가 생기면 기존 public 버킷을 일괄 변경하지 않고 별도 private 버킷과 서명 URL 흐름으로 분리한다.
- **성능(E15):** 로컬 전송량만으로 최적화를 승인하지 않는다. 운영 조건의 LCP·INP·CLS·route JS 기준선을 수집한 뒤 예산을 넘는 항목만 개선한다.
- **CSP(E18):** 즉시 `unsafe-inline`을 삭제하지 않는다. 설치된 Next.js 16 문서에 맞춰 nonce/hash 가능성을 검토하고 Report-Only 관찰 후 강제 정책으로 전환한다.
- **페이지네이션(E09):** 목록 30건 또는 초기 payload 100KB 초과를 전환 검토 기준으로 삼되, 반환 상한에 따른 조용한 누락은 규모와 무관하게 먼저 방지한다.
- **프로젝트 구조화(D02):** 기존 Markdown을 유지하면서 대표 사례 2건을 템플릿으로 먼저 전환한다. 작성 부담과 카드 밀도를 확인한 뒤 DB 필드 추가 여부를 결정한다.

### 3.3 이번 계획의 비목표

- 전면 재제작, 새 프레임워크 도입, Markdown의 Tiptap JSON 전환
- 근거 없는 성과 수치·숙련도 퍼센트 생성
- 댓글·회원가입·결제·구독 기능 추가
- 평가 기준이 정비되기 전 RAG 모델 교체
- 현재 공개 미디어의 일괄 private 전환
- 실제 병목 확인 전 무조건적인 의존성 교체 또는 애니메이션 확대

## 5. 단계별 상세 기획

### 단계 0. 기준선과 회귀 검사 준비

#### 작업

- 운영 DB와 Storage의 백업·복원 지점을 확인하고 staging fixture를 별도로 만든다.
- fixture에는 발행·초안·비공개 글, 대표 이미지 유무, 본문 이미지, 중복 관계가 포함되어야 한다.
- 감사에서 확인된 다음 실패를 재현 테스트로 먼저 고정한다.
  - 관계가 모호한 posts 조회
  - 조회 오류가 빈 배열·404로 변환되는 흐름
  - CMS 업무 오류 뒤 uncontrolled 필드 초기화
  - 즉시 발행 후 화면의 draft 상태 잔류
  - 320px 검색창 overflow
  - 챗봇 내부 이동 후 dialog 잔류와 초기 focus 누락
  - 16% pass rate가 release gate를 통과하는 RAG 반례
- 운영 성능 기준선과 핵심 URL의 현재 응답을 같은 형식으로 기록한다.

#### 산출물

- 실제 DB 관계 계약 테스트와 고정 fixture
- 실패 재현 테스트 목록 및 수정 전 결과
- 운영 기준선 기록: 대표 URL, 콘텐츠 수, 응답 상태, Web Vitals 측정 조건

#### 종료 조건

- 구현자가 어떤 실패를 수정하는지 자동 검사로 재현할 수 있다.
- 운영 데이터에 직접 쓰지 않고 조회·저장·상태 전환을 검증할 staging 경계가 있다.

### 단계 1. 기능과 데이터 신뢰성 복구

#### 1A. 콘텐츠 조회 계약과 장애 상태

대상: `E01`, `E02`, `U06`, `O01`, `O02`, `E17` 일부

- posts의 대표 이미지 관계를 외래 키로 명시하고 본문 이미지 관계와 별칭을 분리한다.
- `not found`, 정상 빈 결과, dependency failure를 반환 타입에서 구분한다.
- 실패를 `[]`, `undefined`, demo profile로 변환해 성공 캐시에 저장하지 않는다.
- demo profile은 명시적인 로컬 데모 모드에서만 사용한다.
- 조회 timeout, stale 성공 데이터 유지, 재시도, 오류 화면 정책을 정의한다.
- readiness는 가벼운 의존성 probe로 유지하되 posts 관계 계약을 확인한다.
- 배포 후 smoke는 홈·블로그 목록·대표 상세·RSS·사이트맵의 실제 제품 결과를 검사한다.

완료 기준:

- 대표 이미지 없음·있음·본문 이미지 포함 fixture가 모두 조회된다.
- 발행 글 수, 상세 200, RSS item 수, 사이트맵 URL 수가 같은 데이터 집합과 일치한다.
- DB 오류는 “글 없음”이 아니라 복구 가능한 오류 상태로 표시되며 실패 cache가 복구를 지연시키지 않는다.
- DB 연결만 성공하고 관계 조회가 실패하는 상황에서 readiness 또는 post-deploy smoke가 실패한다.

#### 1B. CMS 입력 보존과 발행 상태

대상: `E03`, `E04`, `E06`

- 글·프로젝트 폼의 제목, slug, 요약, 태그, 분류, 미디어, 기간, 상태, 본문을 하나의 controlled document state로 통합한다.
- 서버 action은 성공 시 정규화된 저장 값, id, slug, status, version, updatedAt을 반환한다.
- 업무 오류와 예외 모두 입력을 유지하며, 성공 후에만 baseline과 임시 초안을 갱신한다.
- 신규 저장 성공 후 정식 편집 URL로 전환한다.
- dirty 판정과 로컬 복구 범위를 본문에서 전체 문서로 확장하고 문서 ID·사용자·작성 세션별 키를 사용한다.

완료 기준:

- 신규·기존 글과 프로젝트의 검증 실패·중복·충돌·일시 오류 뒤 모든 필드가 보존된다.
- `초안 → 즉시 발행 → 본문 수정 → 일반 저장` 후에도 `published`가 유지된다.
- 제목이나 대표 이미지만 바꾼 경우에도 이탈 경고와 복원이 동작한다.

#### 1C. CSS 계층과 필수 접근성

대상: `E05`, `D09`, `U02`

- 전역 reset을 Tailwind `base` layer로 이동하고 링크·버튼 variant가 유틸리티를 정상적으로 덮어쓰게 한다.
- 전경·배경·링크·버튼·장식 토큰을 분리하고 기존 `!important` 보정을 검토한다.
- 검색 grid track과 item에 실제 축소 가능한 폭을 적용해 320px overflow를 제거한다.
- 기본·선택·hover·focus·disabled 상태를 두 테마에서 검사한다.

완료 기준:

- 감사에서 지적된 6개 대비 항목이 일반 텍스트 4.5:1 등 해당 WCAG 2.2 AA 기준을 충족한다.
- 320·360·390px와 200% 확대에서 검색 입력·필터·결과 안내가 컨테이너 안에 있다.
- 선언한 variant와 브라우저 computed style이 일치한다.

#### 1D. RAG 출시 판정

대상: `O03`

- 전체 성공률, 질문 유형별 성공률, expected-term 성공률, first-token 및 total latency를 명시적인 gate 조건으로 포함한다.
- critical 안전성 조건은 별도 필수 조건으로 유지한다.
- case 누락·중복·미실행을 실패로 판정하고 dataset hash와 실행 결과를 보존한다.
- 기준값은 실제 모델 기준선과 제품 요구를 함께 보고 확정하며 임의로 성공률을 부풀리지 않는다.

완료 기준:

- `50개 중 8개 성공` 반례가 최종 실패한다.
- 정상·오답·지연·case 누락·critical 실패의 단위 테스트가 각각 기대한 gate 결과를 낸다.

### 단계 2. 핵심 사용자 동선과 관리자 사용성

#### 2A. 탐색·문서 구조·문의

대상: `U01`, `U03`, `U04`, `U05`, `U07`, `D08`

- 검색 입력은 로컬 state로 즉시 반영하고 URL 갱신은 debounce 또는 제출 시점으로 분리한다. IME 조합 중에는 URL을 갱신하지 않는다.
- 카드 제목과 주요 시각 영역을 하나의 명확한 링크로 만들고 링크 이름에 콘텐츠 제목을 포함한다.
- 페이지 대표 제목은 `h1`, 하위 섹션은 `h2` 이하로 구성하며 오류 화면의 `main` 소유자를 하나로 제한한다.
- 활성 메뉴는 `aria-current`와 동일한 시각 표시를 갖고 상세에서도 상위 섹션이 활성화된다.
- 문의 페이지는 검증된 콘텐츠 제목·URL을 유지하고 이메일 복사, 성공 안내, 안전하게 인코딩된 subject/body를 제공한다.
- 한국어 제목은 의미 단위 줄바꿈과 반응형 글자 크기를 적용하고 사용자 라벨 언어를 한국어 중심으로 통일한다.

완료 기준:

### 단계 4. 확장·성능·운영 품질

#### 4A. 데이터·렌더링 경계

대상: `E09`, `E11`, `E13`, `E17`

- 홈·목록·상세 projection을 분리하고 목록에서 전체 본문을 제거한다.
- 읽기 시간은 저장 시 계산하며 관리자 목록과 미디어 선택기는 검색·페이지네이션을 준비한다.
- Supabase 생성 Database 타입을 client와 RPC에 연결하고 중요한 외부 응답은 런타임 검증한다.
- Markdown 지원 문법을 문서화하고 괄호 URL, escaped pipe, 중첩 목록, 코드, 중복 제목 fixture를 만든다.
- 렌더링·목차·plain text·RAG 추출이 가능한 한 같은 AST 구조를 공유한다.
- 공개 미디어 정책을 CMS에 안내하고 민감 자료는 별도 private 흐름이 확정되기 전 업로드하지 않는다.

#### 4B. 성능·보안·유지보수

대상: `E15`, `E16`, `E18`

- 정해진 모바일 네트워크·CPU 조건에서 LCP·INP·CLS, TTFB, route JS, 이미지 bytes를 측정한다.
- 결과에 따라 챗봇 지연 로드, sessionStorage 저장 throttle, 이미지 sizes, 폰트 요청을 개선한다.
- `tmp`, `test-results`, 감사 산출물과 제품 lint/typecheck 경계를 명시하고 README의 데모 설명을 실제 fallback 정책과 맞춘다.
- 복잡한 폼·목록·상태 UI는 동작 단위로 분리해 리뷰 가능한 diff를 만든다.
- CSP는 Report-Only로 정상 스크립트·테마 초기화·Sentry를 관찰한 뒤 nonce/hash 강제 전환을 검토한다.

#### 4C. RAG 검색·복구·사실성

대상: `O04`, `O05`, `O06`, `O07`

- RAG 인덱싱 문서에 heading path, 문단, 목록, 표, 의미 있는 코드 설명을 보존하고 chunk metadata에 전달한다.
- LLM 준비 확인을 제한 시간 동안 반복하고 worker claim/fail 경계에 backoff·jitter·종료 신호 처리를 적용한다.
- 인덱싱 지연, 마지막 성공 처리 시각, 지속 장애를 관측하고 알림 소유자를 정한다.
- Python dependency lock 또는 hash가 포함된 constraints와 업데이트 절차를 마련한다.
- 배포 기록에 source SHA, 의존성, 모델·임베딩·프롬프트 revision, migration, smoke 결과를 연결한다.
- 출처 형식 검사와 의미 평가를 분리하고 정답 사실, 허용 표현, 금지 추론, 실제 URL 200 여부를 검사한다.
- 주요 평가 결과는 사람이 근거와 대조하고, 대화 원문을 무분별하게 수집하지 않는 피드백 방식을 사용한다.

완료 기준:

- 같은 글의 서로 다른 절을 묻는 질문이 적절한 heading의 chunk를 검색한다.
- 긴 모델 준비, 짧은 DB 중단, claim/fail 오류 뒤 수동 개입 없이 복구된다.
- 동일 배포 입력으로 Python 환경과 평가 결과를 재현할 수 있다.
- 틀린 수치, 없는 출처 ID, 삭제된 URL, 근거 없는 경력 주장의 반례가 실패한다.

- staging 쓰기 검사는 운영 DB가 아닌 별도 계정과 fixture에서 수행한다.

코드 개선만으로 D01~D07이 완료되지는 않는다. 다음 원본을 준비해야 한다.

- 대표 프로젝트 2건의 기간, 팀 구성, 개인 역할, 제약, 대안, 선택 이유
- 결과 수치의 단위, 데이터 구간, 기준 모델 또는 비교 전 상태
- 공개 가능한 저장소, 논문, 데모, 수상 안내, 발표 자료 URL
- 프로젝트별 핵심 이미지 또는 익명화 가능한 도식 원본
- 공개 가능한 경력·교육·연구·활동 기간과 연결 프로젝트

## 8. 운영 관측과 롤백

### 관측 항목

- 공개 조회 실패율과 posts 관계 probe 상태
- 홈·블로그 목록·대표 상세의 응답 상태 및 예상 콘텐츠 수
- cache 재검증 실패와 마지막 성공 시각
- CMS 저장 오류 유형, 충돌, 발행 상태 전환 실패
- 챗봇 status·stream 실패율, first-token·total latency, length 종료 비율
- worker queue 지연, 마지막 처리 시각, 재시작 횟수
- Web Vitals와 페이지별 전송 예산

### 롤백 원칙

- DB 변경은 순방향 migration으로만 적용하고 확장 단계와 계약 강제 단계를 분리한다.
- 조회 변경은 구버전 데이터와 nullable 관계를 허용한 뒤 fixture로 확인한다.
- CMS 폼 변경은 저장 RPC 계약을 유지하고 새 반환 필드는 호환 가능하게 추가한다.
- CSP는 Report-Only에서 문제 없는 것이 확인되기 전 강제하지 않는다.
- RAG gate 강화로 배포가 막히면 기준을 즉시 낮추지 않고 실패 case와 제품 요구를 검토한다.

## 10. 기존 구현 보존 조건

다음 기반은 개선 과정에서 반드시 회귀 검사하고 유지한다.

- skip link, 공개 main focus 이동, `aria-current`, 모바일 메뉴 Escape·focus 복귀
- 초기 테마 적용, OS 테마 반영, 명시적 선택 저장, 다른 탭의 theme 변경 반영
- Markdown 미리보기·이미지 삽입·임시 저장, 목차, 이전·다음·연관 콘텐츠
- 관리자 권한·서버 검증·원자 저장·상태 전이·편집 버전 충돌 검사
- 이미지 signature·decode·크기 검사, Sharp 재인코딩, metadata, 삭제 방지·outbox
- 공개 필터·RLS, 관리자 noindex, metadata·JSON-LD·RSS·사이트맵 기능
- 챗봇 SSE·입력 제한·취소·재시도·서명·rate limit·출처 URL 제한
- RAG worker의 revision 기반 원자 활성화, Sentry, liveness/readiness, CI와 운영 runbook

## 11. 완료 정의

개별 작업은 다음 조건을 모두 충족해야 완료로 처리한다.

1. 연결된 피드백 ID와 사용자 영향이 PR 또는 변경 기록에 적혀 있다.
2. 수정 전 실패를 재현하고 수정 후 통과하는 자동 검사가 있다.
3. 라이트·다크, 320px 이상 핵심 viewport, 키보드 사용을 확인했다.
4. DB·캐시·발행 상태에 영향을 주면 staging smoke 결과가 있다.
5. 운영 설정 또는 정책이 달라지면 runbook과 README를 함께 갱신했다.
6. 실제 실행하지 않은 staging·운영 검증은 완료로 표시하지 않는다.
7. 기존 구현 보존 조건과 공개 URL 호환성이 유지된다.
