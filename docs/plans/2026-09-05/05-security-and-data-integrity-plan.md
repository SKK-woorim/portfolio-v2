# 보안·데이터 정합성 개선 기획서

- 관련 항목: `SEC-01`~`SEC-03`, `DATA-01`~`DATA-03`
- 우선순위: 전 항목 P0 또는 P1
- 목표: 공개 공격면과 관리자 실수 모두에서 콘텐츠와 계정 상태가 일관되게 유지되게 한다.

## 1. 확인된 핵심 위험

### 로그인 제한 RPC

현재 `is_login_locked`, `record_failed_login_attempt`, `clear_failed_login_attempt`는 `SECURITY DEFINER`이며 `anon`, `authenticated`에 실행 권한이 있다. publishable key만 가진 외부 호출자도 임의 이메일을 대상으로 실패 횟수를 증가시키거나 초기화할 수 있다. 이는 계정 잠금 유발과 제한 우회를 모두 허용하는 구조다.

### 부분 저장

콘텐츠 본문 upsert 후 태그와 대표 이미지 관계를 별도 쿼리로 변경하고, 감사 로그도 별도로 기록한다. 관계 갱신이 실패하면 본문만 저장된 상태가 반환된다. 순서 변경도 여러 UPDATE를 병렬 수행해 일부만 성공할 수 있다. 상태 전이는 기존 상태 조회 후 갱신하므로 동시 요청 충돌을 감지하지 못한다.

### 파일 검증

업로드는 브라우저가 전달한 MIME, 확장자와 파일 크기를 검사한다. 실제 파일 시그니처, 이미지 디코딩 가능 여부, 픽셀 수, 메타데이터는 확인하지 않는다. 허용 형식이 제한되어 있어 SVG 위험은 피하고 있지만 위장 파일과 과대 픽셀 이미지는 추가 방어가 필요하다.

### 스키마 이력

초기 마이그레이션과 후속 보정 마이그레이션에 같은 구조 변경이 중복 반영된 흔적이 있다. 이미 적용된 파일을 수정하면 새 환경과 기존 환경이 서로 다른 경로로 같은 버전 목록에 도달할 수 있다.

## 2. 로그인 제한 재설계

### 요구사항

- 공개 역할에서 카운터 조회·기록·초기화 RPC의 실행 권한을 회수한다.
- 카운터 변경은 신뢰된 서버 환경에서만 수행한다.
- 이메일과 IP 계열 식별자를 각각 제한해 단일 계정 공격과 다계정 분산 시도를 모두 완화한다.
- 계정 존재 여부, 잠금 여부와 내부 오류를 응답 메시지로 구분하기 어렵게 한다.
- 성공 로그인만 실패 카운터를 초기화한다.
- 로그인 제한 저장소 오류는 fail-open이 아닌 명시적 일시 실패로 처리하되 운영자가 원인을 확인할 수 있게 한다.

### 제안 구조

- 브라우저 → Next.js 로그인 Server Action → 신뢰된 제한 저장소 → Supabase Auth 순서를 유지한다.
- 공개 Supabase 클라이언트로 제한 RPC를 호출하지 않는다.
- Vercel Functions에 맞는 외부 KV/Upstash 계열을 새로 도입할지, 제한 목적의 최소 권한 서버 자격증명과 DB 함수를 사용할지 구현 전에 선택한다.
- 식별자는 복원 가능한 이메일 hash 대신 서버 비밀을 사용한 HMAC으로 저장한다.
- 이메일 기준과 IP prefix 기준에 서로 다른 sliding window 또는 token bucket을 적용한다.
- `Retry-After`와 일반화된 오류 문구를 제공한다.

### DB 권한 변경

- 새 순방향 마이그레이션에서 기존 세 함수에 대해 `revoke execute ... from public, anon, authenticated`를 명시한다.
- 필요하면 trusted role 전용 함수를 새 이름으로 만들고 함수 내부에서도 호출 경계를 검증한다.
- 기존 함수를 바로 삭제하면 이전 배포가 깨질 수 있으므로 웹 배포 → 권한 전환 → 정리의 호환 순서를 문서화한다.

## 3. 원자적 CMS 저장

### 3.1 저장 RPC

게시글과 포트폴리오 각각 하나의 DB 함수 또는 공통 명령 구조를 둔다.

```text
save_post_atomic(payload, expected_updated_at)
save_portfolio_atomic(payload, expected_updated_at)
```

트랜잭션 안에서 다음을 모두 수행한다.

1. `is_admin()` 재검증
2. 콘텐츠 행 insert/update
3. 태그 생성과 관계 전체 교체
4. 대표·갤러리·본문 미디어 관계 갱신
5. 감사 로그 기록
6. 변경 이벤트 또는 RAG 동기화 trigger 확정
7. 저장된 ID, slug, updated_at 반환

TypeScript와 DB의 입력 검증 책임을 나눈다. UI 친화적 오류는 Zod가 먼저 확인하고, 권한·FK·상태 전이·관계 정합성은 DB가 최종 보장한다.

### 3.2 동시 편집 방지

- 편집 폼에 조회 당시 `updated_at`을 숨은 값으로 보낸다.
- update는 `WHERE id = p_id AND updated_at = p_expected_updated_at` 조건을 사용한다.
- 일치하는 행이 없으면 덮어쓰지 않고 `다른 곳에서 수정됨` 충돌을 반환한다.
- 관리자는 최신본 다시 불러오기 또는 현재 입력 복사 후 비교를 선택한다.

### 3.3 상태 전이

- 허용 전이표를 DB 함수에 둔다.
- 휴지통 콘텐츠 직접 발행과 이미 영구 삭제된 ID 변경을 거절한다.
- `UPDATE ... WHERE status = expected_status RETURNING`으로 동시에 온 요청 중 하나만 성공시킨다.
- 발행일은 최초 발행일과 최근 재발행 정책을 구분한다. 단순 수정 때마다 현재 시각으로 덮어쓰지 않는다.

### 3.4 순서 변경

- UUID 배열 한 개를 RPC로 전달한다.
- 중복 ID, 누락 ID, 휴지통 ID, 권한 범위를 트랜잭션 안에서 검증한다.
- `unnest(... with ordinality)`로 한 문장에 순서를 갱신한다.
- 영향받은 행 수가 기대값과 다르면 전체를 rollback한다.

## 4. 업로드 보안

### 검사 순서

1. 인증과 관리자 역할 확인
2. 요청 본문 및 파일 크기 상한 확인
3. magic bytes로 실제 형식 판별
4. 이미지 decoder로 읽을 수 있는지 확인
5. width × height와 최대 픽셀 수 확인
6. EXIF·프로필 등 불필요한 메타데이터 제거
7. 허용 형식으로 재인코딩
8. 서버가 결정한 확장자와 UUID key로 저장
9. DB insert 실패 시 Storage 보상 삭제

### 정책

- JPG, PNG, WebP, AVIF만 허용하고 SVG, GIF, PDF는 제외한다.
- 파일 크기 5MB 정책과 별개로 최대 픽셀 수를 둔다. 제안값은 40MP이며 실제 운영 이미지로 검증한다.
- 원본 파일명은 화면 참고값으로만 정규화해 저장하고 Storage key에 직접 사용하지 않는다.
- 업로드된 이미지에서 GPS 등 개인정보 메타데이터를 제거한다.
- 동일 checksum 자산은 중복 업로드를 안내하되 자동 합치기는 사용 관계 확인 후 결정한다.

## 5. CSP와 브라우저 보안

- 현재 production CSP의 `script-src 'unsafe-inline'`은 테마 초기화 script 때문에 유지되고 있다.
- 1차로 고정 script hash 적용 가능성을 확인한다. 요청별 nonce가 필요하면 Next.js 16.3 로컬 문서에 맞춰 동적 렌더링·cache 영향까지 검토한다.
- `style-src 'unsafe-inline'` 제거는 Tailwind와 framework 생성 스타일을 분석한 뒤 별도 단계로 둔다.
- Supabase, Sentry, RAG API의 실제 연결 origin만 `connect-src`에 둔다.
- CSP report-only를 staging에서 먼저 적용하고 위반 보고를 확인한 뒤 차단 정책으로 전환한다.
- 관리자 페이지에는 public 페이지와 동일하거나 더 엄격한 frame, object, base, form 정책을 적용한다.

## 6. 마이그레이션과 타입 규율

- 한번 공유·적용된 마이그레이션 파일은 수정하지 않는다.
- 모든 보정은 더 큰 타임스탬프의 새 SQL 파일에 작성한다.
- migration ledger와 schema dump/checksum을 staging·production별로 기록한다.
- 빈 DB 전체 적용과 직전 운영 스냅샷의 증분 적용을 CI에서 각각 검증한다.
- Supabase 생성 TypeScript 타입을 단일 파일로 관리하고 스키마 변경 시 재생성한다.
- 마이그레이션과 생성 타입이 달라지면 CI가 실패하도록 한다.
- `.temp` 같은 로컬 Supabase 상태 파일은 커밋 대상과 운영 문서 대상에서 분리한다.

## 7. 감사 로그 정책

- 어떤 이벤트가 반드시 남아야 하는지 정의한다: 발행, 비공개, 휴지통, 복원, 영구 삭제, 권한 변경, 로그인 제한 변경, 챗봇 공개 토글.
- 콘텐츠 저장과 같은 정합성 이벤트는 같은 트랜잭션에 넣는다.
- 감사 로그 실패를 무시하지 않고 전체 작업을 rollback하거나 outbox로 전달한다.
- metadata에는 콘텐츠 제목·slug·이전/다음 상태만 담고 본문, 비밀번호, token, 이메일 원문은 넣지 않는다.
- 관리자에서 기간·작업·대상별 조회와 보존 기간을 제공한다.

## 8. 단계별 전환

### 1차: 즉시 차단

- 로그인 제한 RPC의 공개 실행 권한 회수 계획과 호환 배포
- 파일 실제 형식·픽셀 검사
- 감사 로그 오류 관측

### 2차: 데이터 정합성

- 원자적 저장 RPC
- 조건부 상태 전이
- 원자적 순서 변경
- 미디어 사용 관계 통합

### 3차: 구조 안정화

- 마이그레이션 양 경로 CI
- 생성 DB 타입 도입
- CSP report-only와 nonce/hash 전환
- 감사 로그 조회·보존 정책

## 9. 테스트 계획

- publishable key로 제한 RPC를 직접 호출하면 권한 오류가 난다.
- 같은 IP의 여러 이메일과 여러 IP의 같은 이메일 공격이 각각 제한된다.
- 태그·미디어·감사 로그 중 한 단계를 의도적으로 실패시켜도 콘텐츠 전체가 이전 상태로 남는다.
- 두 브라우저에서 같은 글을 수정하면 늦은 저장이 충돌로 거절된다.
- 순서 변경 중 오류가 나도 모든 sort order가 이전 값으로 유지된다.
- MIME만 이미지로 위장한 파일, 깨진 이미지, 5MB 이하 초대형 픽셀 이미지를 거절한다.
- EXIF 위치 정보가 공개 파일에 남지 않는다.
- 빈 DB와 운영 스냅샷 양쪽에서 마이그레이션 후 스키마와 RLS 결과가 같다.
- CSP report-only 결과에서 필요한 origin과 실제 위반을 구분한다.

## 10. 출시와 롤백

- DB와 Storage 백업 후 staging에 새 함수를 적용한다.
- 새 웹 배포가 새 RPC를 사용하는 것을 확인한 뒤 구 RPC 권한을 회수한다.
- 오류율, 저장 충돌률, 업로드 실패율을 관찰한다.
- rollback은 새 웹 코드 복귀와 DB 함수 호환 유지로 수행한다. 이미 변환된 데이터나 마이그레이션 파일을 삭제하지 않는다.
- destructive rollback이 필요한 스키마 변경은 이번 범위에 넣지 않는다.

## 11. 완료 기준

- 외부 공개 클라이언트가 로그인 제한 상태를 임의로 조작할 수 없다.
- 콘텐츠 저장, 관계 갱신, 감사 로그가 모두 성공하거나 모두 실패한다.
- 동시 요청이 조용히 서로를 덮어쓰지 않는다.
- 업로드 파일은 실제 이미지 검사와 메타데이터 제거를 거친다.
- 새 환경과 기존 환경의 마이그레이션 결과가 자동 검증에서 일치한다.
