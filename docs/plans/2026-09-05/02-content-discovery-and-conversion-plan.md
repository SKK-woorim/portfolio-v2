# 콘텐츠 탐색·설득·문의 전환 개선 기획서

- 관련 항목: `UX-01`~`UX-05`
- 주요 사용자: 채용 담당자, 협업 파트너, 기술 콘텐츠 독자
- 목표: 방문자가 필요한 역량과 작업 근거를 빠르게 찾고 자연스럽게 문의까지 이어가게 한다.

## 1. 배경과 문제

현재 홈은 대표 프로젝트와 최신 글을 보여주고, 블로그는 카테고리·태그 필터를 제공한다. 상세 글에는 읽기 시간이 있고 포트폴리오에는 유형·기간·태그·본문·외부 링크가 있다. 그러나 콘텐츠 수가 늘어날 때 필요한 검색, 페이지네이션, 연관 콘텐츠와 상세 목차가 없다.

또한 포트폴리오 설명은 자유형 Markdown 중심이어서 채용 담당자가 역할, 문제, 기여 범위와 결과를 항목 간 일관된 방식으로 비교하기 어렵다. 상세 페이지를 읽은 뒤 문의로 연결되는 CTA도 문맥에 맞춰 설계되어 있지 않다.

## 2. 핵심 목표

- 30초 안에 관심 기술과 관련된 프로젝트 또는 글을 찾게 한다.
- 프로젝트의 `무엇을 만들었는가`보다 `어떤 문제를 어떻게 해결했고 어떤 결과가 있었는가`를 먼저 이해시키게 한다.
- 긴 상세 콘텐츠의 위치 파악과 다음 콘텐츠 이동을 돕는다.
- 문의 CTA의 효과를 개인정보 침해 없이 측정한다.

## 3. 정보 탐색 설계

### 3.1 블로그 검색

- 검색 대상: 제목, 요약, 카테고리, 태그. 본문 전체 검색은 콘텐츠 수와 DB 비용을 측정한 뒤 2차로 확장한다.
- 검색어와 필터는 URL의 `q`, `category`, `tag`, `page`에 보존한다.
- 검색 입력에는 label과 지우기 버튼을 제공하고, 결과 개수와 활성 조건을 문장으로 알린다.
- 필터 조합은 AND로 적용하되 같은 그룹의 여러 태그 지원 여부는 콘텐츠 규모가 커질 때 결정한다.
- 검색어가 없을 때는 최신순, 있을 때는 제목 일치 우선 후 최신순으로 정렬한다.
- 결과가 없으면 조건 초기화와 관련 태그를 제공한다.

초기 구현은 현재 콘텐츠 수가 적으므로 서버에서 받은 목록을 클라이언트가 필터링해도 된다. 30개를 넘거나 payload가 100KB를 넘으면 Supabase의 제한된 검색 쿼리와 서버 페이지네이션으로 전환한다.

### 3.2 포트폴리오 필터

- 기술 태그, 프로젝트 유형, 기간을 기본 필터로 제공한다.
- 채용·협업 관점에서 `AI Agent`, `RAG`, `데이터 파이프라인`, `분석·예측` 같은 역량 묶음을 관리자 데이터로 관리하는 방안을 검토한다.
- 필터 결과에도 홈 대표 여부가 아니라 관리자 노출 순서와 최신성을 일관되게 적용한다.
- 필터를 적용해도 각 카드의 핵심 성과 한 줄은 유지한다.

### 3.3 페이지네이션 도입 기준

- 블로그 또는 포트폴리오가 30건 이상이면 페이지당 12건을 기본으로 한다.
- URL 기반 페이지를 사용해 새로고침, 공유, 검색엔진 탐색을 보장한다.
- 존재하지 않는 페이지는 1페이지로 조용히 돌리지 않고 유효한 마지막 페이지 또는 404 정책을 명확히 정한다.
- 필터 변경 시 1페이지로 이동한다.

## 4. 상세 페이지 경험

### 4.1 목차와 읽기 위치

- 본문에 `h2`가 3개 이상일 때만 목차를 표시한다.
- 제목에서 안정적인 heading ID를 만들고 중복 제목에는 순번을 붙인다.
- 데스크톱은 sticky aside, 모바일은 접을 수 있는 `이 글의 내용` 블록을 사용한다.
- 현재 읽는 절을 강조하되, 강조가 없어도 링크와 문서 순서만으로 사용할 수 있어야 한다.
- 읽기 진행률은 보조 요소로만 사용하고 `prefers-reduced-motion`을 존중한다.

### 4.2 연관 콘텐츠와 이전·다음

- 블로그 연관도: 공통 태그 수, 같은 카테고리, 최신성을 순서대로 반영한다.
- 포트폴리오 연관도: 공통 기술 태그, 유형, 기간을 반영한다.
- 동일 콘텐츠는 제외하고 최대 3건을 표시한다.
- 이전·다음은 현재 정렬 기준에서 결정하며 제목을 함께 표시한다.
- 연관 결과가 없으면 억지로 채우지 않고 목록 이동 CTA만 제공한다.

### 4.3 프로젝트 사례 구조

기존 Markdown을 유지하면서 비교 가능한 구조화 필드를 단계적으로 추가한다.

| 필드 | 목적 | 노출 |
| --- | --- | --- |
| 역할 | 본인의 책임과 의사결정 범위 | 상세 요약 패널 |
| 팀·기간 | 작업 맥락 | 상세 요약 패널 |
| 문제 | 해결 전 상태와 제약 | 상세 첫 절 |
| 접근 | 설계·도구 선택과 이유 | 상세 본문 |
| 결과 | 수치 또는 검증 가능한 변화 | 카드와 상세 강조 |
| 기술 | 구현 수단 | 카드·필터·상세 |
| 회고 | 배운 점과 다음 개선 | 상세 마지막 절 |

- 수치가 없는 프로젝트에 가짜 지표를 요구하지 않는다. 대신 `처리 흐름 단순화`, `재현 가능한 배포`처럼 검증 가능한 정성 결과를 기록한다.
- 기존 콘텐츠 2건을 먼저 새 구조로 변환해 카드 밀도와 작성 부담을 검증한다.
- 구조화 필드가 비어 있으면 기존 요약과 Markdown만으로 정상 렌더링한다.

## 5. 문의 전환 설계

### 5.1 CTA 배치와 문구

- 블로그 상세 하단: `이 주제로 함께 이야기하기`
- 포트폴리오 상세 하단: `비슷한 문제를 함께 해결하기`
- 홈과 연락처: 기존 협업 문의를 유지한다.
- 모든 CTA는 `/contact?from=portfolio&slug=...`처럼 출발 문맥을 URL에 담을 수 있다.
- 연락 페이지는 출발 콘텐츠 제목을 짧게 보여주되 이메일 본문을 자동 전송하지 않는다.

### 5.2 측정 이벤트

- `content_view`: 상세 경로와 콘텐츠 유형
- `contact_cta_click`: 출발 경로와 콘텐츠 식별자
- `email_link_click`: 출발 경로
- `external_project_link_click`: 링크 유형

이메일 주소, 질문 내용, 챗봇 대화 원문은 분석 이벤트에 넣지 않는다. 분석 도구 도입 전 이벤트 명세만 확정하고, 운영자가 실제로 볼 지표가 없으면 수집하지 않는다.

## 6. 데이터와 구현 방향

- 검색·필터용 상태는 URL을 기준으로 하고 전역 상태 관리 라이브러리를 추가하지 않는다.
- 콘텐츠 수가 적은 동안은 현재 목록 cache를 재사용한다.
- 서버 검색 전환 시 제목·요약·태그에 필요한 인덱스를 측정 후 추가한다.
- 구조화 프로젝트 필드는 nullable로 추가하고 기존 행을 깨뜨리지 않는다.
- heading ID와 목차 생성은 공개 렌더러의 동일한 Markdown 파싱 결과를 사용한다.
- 연관 콘텐츠 계산은 처음에는 서버에서 작은 목록을 이용하고, 규모가 커지면 DB 함수 또는 별도 쿼리로 이동한다.

## 7. 접근성과 반응형

- 현재 선택된 필터에는 시각 스타일과 `aria-current` 또는 적절한 pressed 상태를 함께 제공한다.
- 검색 결과 갱신은 focus를 강제로 이동하지 않고 결과 개수를 live region으로 알린다.
- 목차 링크는 고정 헤더 높이를 고려해 제목이 가려지지 않게 한다.
- 200% 확대에서 sticky 목차가 본문을 가리지 않으며 한 열로 전환된다.
- 카드 전체 링크 안에 별도 중첩 링크를 두지 않는다.

## 8. 성공 지표

출시 전 기준선과 출시 후 4주를 같은 조건으로 비교한다.

| 지표 | 해석 | 목표 방향 |
| --- | --- | --- |
| 상세 페이지 도달률 | 목록이 콘텐츠 탐색으로 이어지는가 | 상승 |
| 검색·필터 후 상세 클릭률 | 탐색 도구가 유용한가 | 상승 |
| 상세 → 문의 CTA 클릭률 | 콘텐츠가 협업 의도로 연결되는가 | 상승 |
| 검색 결과 없음 비율 | 분류·검색어가 콘텐츠와 맞는가 | 감소 또는 원인 분류 |
| 연관 콘텐츠 클릭률 | 연속 탐색에 도움이 되는가 | 측정 후 기준 설정 |

## 9. 단계별 구현

### 1차

- 블로그 검색, 결과 개수, URL 상태
- 상세 이전·다음과 연관 콘텐츠
- 상세 하단 문의 CTA와 이벤트 명세

### 2차

- 포트폴리오 필터
- 긴 글 목차와 현재 절 표시
- 프로젝트 구조화 필드와 관리자 입력 UI

### 3차

- 콘텐츠 규모 기준을 넘을 때 서버 페이지네이션
- 실제 사용 데이터에 따른 정렬·추천 보정

## 10. 테스트 계획

- 검색·필터·페이지 URL을 직접 열어도 같은 결과가 나온다.
- 한글, 영문, 특수문자, 빈 검색어와 존재하지 않는 태그를 처리한다.
- 연관 콘텐츠가 자기 자신과 비공개 항목을 포함하지 않는다.
- 같은 제목이 여러 번 등장해도 목차 ID가 고유하다.
- 구조화 필드가 모두 비어 있는 기존 프로젝트가 깨지지 않는다.
- CTA 이벤트에 이메일과 본문 데이터가 포함되지 않는다.
- 모바일, 키보드, 200% 확대에서 검색과 목차를 사용할 수 있다.

## 11. 완료 기준

- 방문자는 제목·요약·태그로 원하는 글을 검색하고 상태가 담긴 URL을 공유할 수 있다.
- 긴 글은 목차로 이동할 수 있고 상세 하단에서 관련 콘텐츠를 이어 볼 수 있다.
- 대표 프로젝트는 역할, 문제, 접근, 결과를 일관된 순서로 설명한다.
- 문의 CTA의 출발 문맥과 클릭 성과를 개인정보 없이 확인할 수 있다.
