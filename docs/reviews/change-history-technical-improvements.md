# 변경 이력 기반 기술 개선 분석

## 1. 문서 목적과 분석 범위

이 문서는 Git 변경 이력에서 반복된 결함 유형과 현재 작업 트리의 변경 방향을 추적해, 문제의 기술적 원인과 우선순위별 개선 방안을 정리한다. 단순 기능 목록이 아니라 다음 질문에 답하는 것을 목적으로 한다.

- 어떤 문제가 실제 커밋을 통해 반복적으로 수정되었는가?
- 현재 구조에서 같은 유형의 회귀가 다시 발생할 수 있는 지점은 어디인가?
- 보안, 데이터 정합성, 배포 안정성, 테스트 가능성을 어떤 순서로 개선해야 하는가?

분석 기준 시점은 **2026-08-21 UTC**이며, 범위는 최초 커밋 `8e8e4a5`부터 현재 `HEAD`인 `cf1482e`까지의 커밋 10개와 현재 미커밋 작업 트리다. 미커밋 변경은 아직 확정된 이력이 아니므로 커밋 이력과 구분해 평가했다.

분석에 사용한 근거는 `git log --reverse --stat`, 각 수정 커밋의 `git show`, 현재 `git diff`와 `git status`, 테스트·린트·타입 검사·프로덕션 빌드 결과다.

## 2. 요약

현재 프로젝트는 공개 포트폴리오와 관리자 CMS의 핵심 흐름을 구현했고, Markdown 안전 URL 검사, RLS, 감사 로그, 콘텐츠 휴지통 복구, 캐시 무효화, Sentry 설정 등 좋은 방어 장치를 갖추고 있다. 현재 작업 트리 기준으로 단위 테스트, 타입 검사, 린트, 프로덕션 빌드도 통과한다.

다만 변경 이력은 초기 구현 이후 인증과 권한 문제를 연속적으로 보완한 형태다. 특히 로그인 제한용 `SECURITY DEFINER` RPC가 익명 역할에 노출되어 있고, CMS의 복합 저장이 여러 독립 쿼리로 수행되며, 적용된 초기 마이그레이션을 후속 커밋에서 수정한 흔적이 있다. 이 세 가지는 각각 **보안 우회**, **부분 저장**, **환경별 스키마 불일치**로 이어질 수 있으므로 먼저 개선해야 한다.

현재 미커밋 변경은 단순 디자인 변경이 아니라 공개 조회 payload 축소, 데이터 캐시, 정적 생성, 이미지 최적화, 검색 메타데이터, 구조화 데이터, Sentry와 보안 헤더를 포함하는 **사이트 최적화 작업**이다. 방향은 타당하지만 운영 DB가 비었거나 일시적으로 실패했을 때 데모 콘텐츠를 정상 데이터처럼 반환하고 그 결과를 최대 1시간 캐시하는 동작은 장애를 숨길 수 있다. 또한 Next.js 16.3.0에서 이미 대체된 `unstable_cache`를 새 코드가 사용하므로 후속 전환 계획이 필요하다.

### 이력에서 보이는 반복 패턴

1. **기능 구현 뒤 운영 경계 수정**: 권한 부여, 만료 초대, 복구 URL, 로그인 제한이 최초 기능 이후 별도 수정으로 이어졌다.
2. **DB와 앱의 동시 변경**: 로그인 제한과 휴지통 기능은 SQL과 Server Action을 동시에 변경한다. 배포 순서 또는 일부 실패 시 호환성 검증이 중요하다.
3. **테스트의 사후 보강**: Markdown과 로그인 테스트가 문제 발견 이후 추가됐다. 핵심 보안·RLS·마이그레이션은 아직 실제 DB 통합 테스트가 없다.
4. **큰 초기 커밋**: 잠금 파일을 제외해도 애플리케이션, DB, 인증, 배포가 한 커밋에 묶였다. 기능별 검토와 회귀 지점 추적이 어려워졌다.

## 4. 현재 작업 트리의 방향과 위험

최종 재검토 시점에는 추적 파일 44개 수정과 미추적 파일 14개를 포함한 대규모 작업이 진행 중이었다. 이는 아직 커밋된 변경 이력이 아니며 다음과 같이 평가한다.

### 긍정적인 변화

- `package.json`의 `latest` 의존성을 정확한 버전으로 고정해 재현성을 높였다.
- 공개 콘텐츠 조회에 서버 전용 경계, 캐시 태그, Sentry 오류 수집을 도입했다.
- 사이트 메타데이터, OG 이미지, `robots`, `sitemap`, RSS, manifest를 구체화했다.
- CSP, HSTS, Referrer Policy, Permissions Policy 등의 응답 헤더를 추가했다.
- `/api/health`와 Sentry 클라이언트·서버 설정을 추가했다.
- 관리자 전용 `robots` 메타데이터와 캐시 갱신 시 `updateTag`를 추가했다. Server Action 직후 최신 데이터를 읽어야 하는 현재 용도와 맞는다.

### 커밋 전 반드시 확인할 변화

- `AuthRecoveryRedirect`를 모든 경로가 공유하는 루트 레이아웃에서 실제 대상 경로인 홈으로 이동했다. 전역 client boundary를 줄이면서 `/`로 돌아오는 구형 복구 링크도 계속 처리하는 합리적인 최적화다. 다만 이 동등 동작을 보장하는 회귀 테스트가 없어 Supabase Redirect URL과 구형 링크 시나리오는 커밋 전에 확인해야 한다.
- DB 오류 또는 빈 조회 결과를 데모 콘텐츠로 대체한다. 운영 장애와 “게시물 0개”라는 정상 상태가 구분되지 않고, 대체 결과가 1시간 캐시될 수 있다.
- `unstable_cache`는 설치된 Next.js 16 문서에서 `use cache`로 대체된 API다. 현재 동작하더라도 신규 구현의 장기 기준으로 삼으면 마이그레이션 비용이 생긴다.
- 캐시, Sentry, SEO, 미디어 연결, 보안 헤더가 하나의 큰 미커밋 묶음에 섞여 있다. 회귀 원인과 롤백 단위를 분명히 하려면 관심사별 커밋으로 나누는 편이 안전하다.

## 5. 발견된 사이트 최적화 변경 분석

이 절은 현재 미커밋 변경 중 사이트 성능, 검색 노출, 전송 효율, 사용자 경험에 직접 영향을 주는 내용을 별도로 분류한 것이다. 아직 전후 실측 결과가 없으므로 “구현된 최적화”와 “검증된 성능 향상”을 구분해야 한다.

### 5.1 데이터 조회와 캐시 최적화

#### 발견된 변경

- 공개 콘텐츠 저장소에 `server-only` 경계를 추가해 브라우저 번들로 서버 데이터 접근 코드가 섞이는 것을 방지했다.
- 사용자 쿠키가 필요 없는 공개 조회용 Supabase 클라이언트를 분리했다. `persistSession`, `autoRefreshToken`, URL 세션 감지를 끈 stateless 클라이언트라 공개 페이지의 정적 렌더링과 공유 캐시에 적합하다.
- 목록 쿼리에서 `select("*")`와 본문 전체 조회를 제거하고 제목, 요약, 태그, 대표 이미지 등 카드에 필요한 컬럼만 요청한다. `content_json`과 링크는 상세 쿼리에서만 읽는다.
- 이전 상세 조회는 전체 목록을 불러온 뒤 slug를 메모리에서 찾았지만, 변경 후 `.eq("slug", slug).maybeSingle()`로 대상 행만 조회한다.
- `unstable_cache`에 profile, portfolio, posts 태그와 3,600초 재검증 시간을 부여했다.
- React `cache`로 같은 렌더 요청에서 `generateMetadata`와 페이지 본문이 동일 상세 데이터를 요청할 때 중복 실행을 줄이려는 구조를 추가했다.
- CMS Server Action은 `updateTag`와 `revalidatePath`를 함께 호출해 저장 직후 관리자가 최신 공개 데이터를 읽도록 했다.

#### 기대 효과

- 목록 응답 크기, PostgreSQL row serialization, 네트워크 전송량과 Markdown 변환 비용이 줄어든다.
- 방문 요청마다 Supabase를 호출하지 않아 TTFB와 DB 부하가 낮아질 수 있다.
- 공개 조회가 사용자 세션과 분리되어 여러 방문자가 같은 캐시 결과를 재사용할 수 있다.

#### 남은 문제와 개선

- DB 오류·빈 결과·404를 데모 데이터로 바꾼 결과까지 성공 캐시에 저장할 수 있다. 운영 fallback 정책을 먼저 분리해야 한다.
- portfolio/posts 단일 태그가 목록과 모든 상세 페이지를 함께 무효화한다. 콘텐츠 수가 늘면 `portfolio:{slug}`, `post:{slug}` 상세 태그와 목록 태그를 분리한다.
- Next.js 16 문서상 `unstable_cache`는 `use cache`로 대체됐다. Cache Components 도입 여부를 정한 뒤 `use cache`와 `cacheTag`로 전환한다.
- 실제 개선량은 Supabase query duration, cache hit ratio, TTFB p50/p95, 응답 payload byte를 변경 전후로 비교해야 한다.

### 5.2 정적 생성과 렌더링 최적화

#### 발견된 변경

- 블로그와 포트폴리오 상세 페이지에 `generateStaticParams`를 추가해 빌드 시 공개 slug를 정적 생성한다.
- 프로덕션 빌드 결과 공개 홈, 소개, 연락처, 목록은 1시간 재검증 정적 페이지로 생성됐고, 포트폴리오 4개와 블로그 3개 상세 경로는 SSG 결과로 확인됐다.
- 블로그의 URL 필터 처리를 `Suspense` 아래로 격리해 `useSearchParams`를 사용하는 클라이언트 경계를 명시했다.
- `AuthRecoveryRedirect`를 루트 레이아웃에서 홈으로 내렸다. `/`의 구형 인증 링크 처리는 유지하면서 나머지 공개·관리자 경로가 이 client component를 공통으로 포함하지 않게 했다.

#### 기대 효과

- 캐시가 준비된 공개 페이지는 매 요청 서버 렌더보다 빠르게 전달될 수 있다.
- 상세 페이지의 초기 HTML과 검색 크롤러 접근성이 개선된다.
- 인증 복구 호환 코드의 hydration 범위가 전체 사이트에서 실제 대상 페이지로 축소된다.

#### 남은 문제와 개선

- `generateStaticParams`가 사용하는 목록 함수가 운영 오류 시 데모 slug를 반환하면 실제 운영 콘텐츠가 아닌 데모 경로가 빌드될 수 있다.
- 블로그 필터는 모든 `BlogPost[]`를 클라이언트 컴포넌트에 전달한다. 글 수가 늘면 RSC payload와 hydration 비용이 증가하므로 서버에서 `searchParams`를 받아 필터하거나 페이지네이션한다.
- 정적 생성 경로 수가 커지면 빌드 시간이 선형 증가할 수 있다. 콘텐츠 규모에 따라 인기 경로만 사전 생성하고 나머지는 요청 시 캐시하는 전략을 검토한다.
- 빌드 성공은 런타임 성능 향상의 증거가 아니다. 배포 환경에서 cache cold/warm TTFB와 LCP를 각각 측정한다.

### 5.3 이미지와 전송 최적화

#### 발견된 변경

- 카드, 상세 대표 이미지, 홈 hero, 연락처 이미지에 `next/image`를 적용했다.
- 각 배치에 `sizes`를 지정해 viewport와 그리드 폭에 맞는 responsive image 후보를 선택하게 했다.
- 홈 hero, 첫 featured project, 상세 상단 이미지만 `priority`로 지정해 LCP 후보를 선로드하고, 나머지는 기본 지연 로딩을 유지한다.
- Supabase Storage만 `remotePatterns`에 등록해 이미지 최적화 프록시의 원격 소스를 제한했다.
- 최적화 이미지 캐시의 `minimumCacheTTL`을 2,592,000초(30일)로 설정했다.
- 목록 조회에서는 대표 이미지 URL과 alt만 가져오고 본문 이미지는 가져오지 않는다.

#### 기대 효과

- 원본 크기 그대로 전송하는 것보다 화면 폭에 가까운 파생 이미지를 전달해 모바일 전송량을 줄일 수 있다.
- 이미지 영역의 aspect ratio와 `fill` 컨테이너가 레이아웃 이동을 줄인다.
- LCP 후보만 우선순위를 높여 중요하지 않은 이미지가 초기 대역폭을 선점하는 것을 줄인다.

#### 남은 문제와 개선

- 원본 `public/og.png`는 약 728KB이고 연락처 PNG는 약 1.3MB다. Next Image가 화면용 파생본을 만들더라도 OG crawler는 `og.png` 원본을 직접 가져가며, 첫 이미지 최적화 요청은 원본 decode 비용을 부담한다.
- 사진 성격의 원본은 WebP/AVIF로 내보내고, OG 이미지는 시각 품질을 유지하는 범위에서 200~400KB 수준을 목표로 압축한다. 변환 후 실제 소셜 미리보기 호환성을 확인한다.
- 30일 TTL은 동일 URL의 이미지 교체 반영을 늦출 수 있다. 업로드 key에 content hash 또는 immutable UUID를 유지하고 교체 시 새 URL을 발급해야 한다.
- `priority` 대상이 실제 LCP인지 Lighthouse trace로 확인한다. 화면에 따라 hero와 프로젝트 이미지가 동시에 priority가 되면 초기 대역폭 경합이 생길 수 있다.
- Markdown 본문의 외부 `<img>`는 `next/image` 최적화를 거치지 않는다. CMS 미디어로 통합하거나 이미지 proxy/allowlist 정책을 적용한다.

### 5.4 검색·공유 최적화

#### 발견된 변경

- `metadataBase`와 Vercel/운영 URL fallback을 단일 `site-metadata.ts`에서 관리한다.
- 전체 페이지에 title, description, canonical, Open Graph, Twitter card를 추가했다.
- 블로그 상세는 CMS의 `seo_title`, `seo_description`, 발행일, 수정일, 태그와 대표 이미지를 article metadata로 사용한다.
- 홈에는 `Person`, 블로그에는 `BlogPosting`, 포트폴리오에는 `CreativeWork` JSON-LD를 추가했다. JSON 직렬화 결과의 `<`를 escape해 script 종료 문자열 삽입 위험을 낮췄다.
- sitemap의 모든 콘텐츠에 빌드 시각을 넣던 방식에서 실제 `updated_at`을 사용하도록 변경했다. 검색 엔진에 불필요한 전체 갱신 신호를 보내지 않는다.
- `robots.txt`, 관리자 `noindex`, RSS, web manifest, SVG icon, 1200×630 OG 이미지를 추가·정비했다.

#### 기대 효과

- 중복 URL의 canonical 신호, 소셜 공유 카드, 검색 결과 설명과 콘텐츠 갱신 신호가 정확해진다.
- 구조화 데이터가 페이지의 작성자와 콘텐츠 유형을 검색 엔진이 이해하는 데 도움을 준다.
- 관리자 화면의 색인 가능성을 이중으로 낮춘다.

#### 남은 문제와 개선

- JSON-LD 문법이 유효하다는 것과 검색 엔진이 rich result로 채택한다는 것은 다르다. Schema validator와 실제 배포 URL 검사 결과를 CI 또는 배포 체크리스트에 포함한다.
- 환경 변수 누락 시 `localhost:3000` canonical이 생성될 수 있다. production build에서는 `NEXT_PUBLIC_SITE_URL` 또는 Vercel production URL 부재를 실패 조건으로 검증한다.
- OG 이미지, canonical, sitemap, RSS가 preview domain과 production domain에서 어떤 URL을 사용해야 하는지 정책을 명확히 한다.
- 사이트맵의 DB 오류가 데모 경로 생성으로 이어지지 않게 fallback 정책을 분리한다.

### 5.5 사용자 경험·접근성 최적화

#### 발견된 변경

- 반응형 모바일 메뉴, URL 기반 블로그 category/tag 필터와 빈 결과 상태를 추가했다.
- focus ring, nav `aria-label`, 메뉴 `aria-expanded`, 장식 아이콘 `aria-hidden`, 이미지 alt fallback을 일관되게 추가했다.
- 다크/라이트 테마를 `localStorage`에 유지하고 본문 렌더 전에 작은 초기화 script를 실행해 테마 깜빡임을 줄였다.
- 디자인 토큰과 responsive grid를 확장해 화면 크기별 콘텐츠 계층을 정리했다.

#### 남은 문제와 개선

- 테마 초기화 inline script 때문에 CSP의 `'unsafe-inline'` 허용에 의존한다. nonce/hash 적용 또는 프레임워크가 지원하는 안전한 초기화 방식과 성능을 비교한다.
- 테마 토글은 저장값이 없을 때 OS의 `prefers-color-scheme`을 읽지 않고 dark로 고정한다. 시스템 설정 존중 여부를 제품 정책으로 결정한다.
- 필터 Link에 현재 선택 상태를 나타내는 `aria-current`를 추가하고, 키보드·스크린리더 흐름을 E2E로 검사한다.
- 색 대비, reduced motion, 키보드 탐색과 CLS를 자동 접근성 검사와 실제 기기에서 확인한다.

### 5.6 관측성·빌드 최적화

#### 발견된 변경

- Sentry client/server/edge 초기화와 Next.js 빌드 플러그인을 추가했다.
- 운영 build에서 Sentry debug logging 제거를 활성화하고, 인증 토큰이 있을 때만 sourcemap 처리를 수행한다.
- health endpoint와 오류 페이지 보고를 추가해 배포 후 기본 상태 확인과 오류 추적 경로를 만들었다.
- 모든 패키지의 `latest`를 정확한 버전으로 고정해 동일 lockfile에서 빌드 결과가 바뀌는 위험을 줄였다.

#### 남은 문제와 개선

- Sentry 도입은 런타임 JS와 네트워크 비용을 추가할 수 있다. client bundle 크기와 event sampling 비율을 측정하고 필요한 integration만 유지한다.
- health endpoint는 liveness만 제공한다. DB readiness와 캐시 오류율은 별도 지표가 필요하다.
- 번들 분석 결과가 없으므로 패키지 고정과 tree-shaking 설정만으로 JS 감소를 주장할 수 없다. route별 client JS와 source map 제외 production artifact를 전후 비교한다.

### 5.7 최적화 검증 기준

현재 확인된 것은 코드 구조와 빌드 산출 방식이며, Core Web Vitals 개선 수치는 아직 없다. 최적화 완료 기준을 다음처럼 수치화한다.

| 영역 | 측정 항목 | 제안 기준 |
| --- | --- | --- |
| 사용자 성능 | 모바일 p75 LCP / INP / CLS | LCP ≤ 2.5초, INP ≤ 200ms, CLS ≤ 0.1 |
| 서버 성능 | cache cold/warm TTFB p50·p95 | 배포 전후 수치 기록, warm p95 회귀 방지 |
| 데이터 | Supabase 호출 수·query duration·payload bytes | 목록/상세별 기준선 대비 감소 확인 |
| 이미지 | hero/카드 실전송 bytes, 올바른 `srcset` 후보 | viewport보다 과도한 원본 전송 없음 |
| JavaScript | route별 client JS와 hydration 시간 | BlogBrowser·Sentry·theme 도입 전후 비교 |
| 검색 | canonical, JSON-LD, sitemap, robots | 배포 URL 기준 validator 오류 0건 |
| 접근성 | 키보드, 대비, 이름/역할/상태 | 자동 검사 critical/serious 0건 및 수동 smoke 통과 |

측정은 동일한 배포 환경, 동일 콘텐츠, cold/warm 조건을 고정해 최소 3회 수행하고 중앙값과 p95를 기록한다. 실사용 데이터가 쌓이면 lab Lighthouse 점수보다 field Web Vitals를 우선 판단 기준으로 사용한다.

## 6. 문제점과 기술적 개선 방안

### P0. 로그인 제한 RPC가 익명 호출자에게 노출됨

#### 문제

`202608060001_fix_login_rate_limiting.sql`은 다음 세 함수를 `anon`, `authenticated`에 모두 허용한다.

- `is_login_locked(text)`
- `record_failed_login_attempt(text)`
- `clear_failed_login_attempt(text)`

세 함수는 `SECURITY DEFINER`이므로 호출자 자신의 RLS 권한이 아니라 함수 소유자의 권한으로 실행된다. 외부 호출자는 임의 이메일을 인자로 `record_failed_login_attempt`를 반복 호출해 계정을 잠글 수 있고, 반대로 `clear_failed_login_attempt`를 호출해 제한을 해제할 수 있다. 따라서 현재 제한은 공격자에 의한 계정 잠금과 제한 우회를 모두 허용한다. 이메일 단일 키만 사용하므로 분산 공격과 특정 계정 대상 서비스 거부에도 취약하다.

#### 개선

1. 공개 역할에서 세 RPC의 실행 권한을 회수하는 **새로운 순방향 마이그레이션**을 추가한다. 이미 적용된 이전 파일은 수정하지 않는다.
2. 로그인 제한 저장소는 신뢰된 서버 경계만 갱신하게 한다. 별도 서버 전용 클라이언트를 사용한다면 목적을 로그인 제한으로 한정하고 해당 자격 증명을 브라우저에 노출하지 않는다.
3. 키를 `HMAC(normalized_email) + HMAC(client_ip_prefix)` 조합으로 구성하고, 서버 비밀값 없이 복원 가능한 단순 SHA-256 식별자는 피한다.
4. 고정 창보다 token bucket 또는 sliding window를 적용하고 이메일 키와 IP 키에 서로 다른 한도를 둔다.
5. 응답 메시지와 처리 시간은 계정 존재 여부 및 잠금 여부를 외부에서 구분하기 어렵게 유지한다.
6. 성공 시 초기화는 인증 성공이 확인된 신뢰된 코드 경로에서만 실행한다.

#### 완료 기준

- publishable key만 가진 클라이언트가 세 RPC를 직접 호출하면 권한 오류가 발생한다.
- 같은 IP의 다계정 공격과 다중 IP의 단일 계정 공격을 각각 제한하는 테스트가 있다.
- 성공 로그인, 잘못된 비밀번호, Supabase 일시 오류가 서로 다른 카운터 결과를 갖는 통합 테스트가 있다.

### P0. CMS 복합 변경이 원자적이지 않음

#### 문제

`savePortfolio`는 본문 저장 후 태그와 대표 이미지를 `Promise.all`로 동기화한다. `syncTags`는 기존 관계를 먼저 삭제한 다음 태그를 삽입한다. 중간 단계가 실패하면 본문은 저장됐지만 태그가 사라지거나 대표 이미지만 바뀐 부분 저장 상태가 된다. `reorderPortfolioItems`도 항목별 UPDATE를 병렬 실행하므로 일부 쿼리만 성공할 수 있다. 콘텐츠 상태 변경은 “현재 상태 조회 → 갱신” 두 단계라 동시에 두 요청이 들어오면 오래된 상태를 기준으로 덮어쓸 수 있다. 감사 로그 실패는 호출자가 확인하지 않아 실제 변경과 감사 기록도 어긋날 수 있다.

#### 개선

- 저장, 관계 교체, 감사 로그를 하나의 PostgreSQL 함수/RPC 트랜잭션으로 묶는다. 함수 내부에서도 `is_admin()`을 확인하고 입력 JSON을 구조적으로 검증한다.
- 상태 전이는 `UPDATE ... WHERE id = p_id AND status = p_expected_status RETURNING ...` 형태의 조건부 갱신으로 경쟁 상태를 감지한다.
- 순서 변경은 UUID 배열을 받아 `unnest(... ) WITH ORDINALITY`로 한 번에 갱신한다. 요청 ID의 중복, 누락, 권한 범위와 실제 갱신 행 수를 트랜잭션 안에서 검증한다.
- 감사 로그를 필수 정합성 데이터로 볼 경우 같은 트랜잭션에 포함한다. 비필수 원격 관측 이벤트라면 DB 변경 후 outbox에서 비동기로 전송한다.

#### 완료 기준

- 태그 또는 미디어 관계 삽입을 의도적으로 실패시켜도 본문과 기존 관계가 모두 원상태로 남는다.
- 동시에 발행/휴지통 요청을 보내면 한 요청만 성공하고 다른 요청은 충돌 응답을 받는다.
- 순서 변경 도중 오류가 발생해도 전체 순서가 이전 상태로 유지된다.

### P1. 적용된 마이그레이션 파일의 후속 수정으로 스키마 이력이 분기됨

#### 문제

`1a394f6`은 새 로그인 제한 마이그레이션을 추가하면서 이전 `202608050001_initial_schema.sql`의 `pgcrypto` 설치 위치와 함수 본문도 수정했다. `cf1482e` 역시 새 휴지통 마이그레이션을 추가하면서 초기 마이그레이션에 같은 컬럼을 미리 넣었다.

이미 초기 마이그레이션을 적용한 환경은 수정된 파일을 다시 실행하지 않지만, 새 환경은 수정된 초기 파일을 실행한다. 결과적으로 동일한 마이그레이션 버전 목록을 가진 환경이 서로 다른 경로로 스키마에 도달한다. `IF NOT EXISTS`가 일부 중복 실행을 숨겨도 함수 정의, 확장 스키마, 권한과 같은 차이는 남을 수 있다.

#### 개선

- 한 번 공유되거나 배포된 마이그레이션은 불변으로 취급한다. 모든 수정은 타임스탬프가 더 큰 새 파일에 작성한다.
- 현재 기대 스키마를 만드는 보정 마이그레이션을 추가하고, 개발·스테이징·운영 각각의 적용 버전과 스키마 체크섬을 기록한다.
- CI에서 빈 DB에 전체 마이그레이션을 적용하는 경로와, 직전 운영 스냅샷에서 증분 적용하는 경로를 모두 검사한다.
- `anon`, `authenticated` 역할로 대표 SELECT/INSERT/RPC를 실제 호출해 GRANT와 RLS를 함께 검증한다.
- Supabase 생성 타입을 `src/lib/supabase/database.types.ts` 같은 단일 파일로 관리하고, 스키마 변경 후 타입 diff가 없으면 CI가 실패하도록 한다.

### P1. 데모 fallback이 운영 장애와 정상 빈 상태를 숨김

#### 문제

현재 미커밋 `repository.ts`는 다음 경우 모두 데모 데이터를 반환한다.

- Supabase 설정이 없음
- DB 요청 오류
- 목록 조회 결과가 0건
- 상세 slug가 존재하지 않음

이 정책은 로컬 미리보기에는 편리하지만 운영에서는 삭제·비공개 처리된 콘텐츠가 데모 데이터로 다시 노출될 수 있다. 일시 오류로 만들어진 데모 결과가 `unstable_cache`에 저장되면 DB가 복구된 뒤에도 최대 1시간 잘못된 화면을 제공할 수 있다. Sentry 이벤트가 남더라도 방문자는 장애를 정상 콘텐츠로 인식한다.

#### 개선

- fallback 허용 여부를 환경 정책으로 분리한다. Supabase 설정이 없는 로컬 개발에서만 데모 데이터를 허용한다.
- 운영의 빈 목록은 빈 배열로, 없는 상세 slug는 `undefined`로 반환해 `notFound()`로 연결한다.
- 운영 DB 오류는 구조화된 오류로 전파해 오류 UI 또는 마지막으로 검증된 캐시를 사용한다. 오류로 만든 데모 결과를 성공 캐시에 넣지 않는다.
- 목록과 상세 태그를 `posts`, `post:{slug}`처럼 분리해 한 글 변경이 전체 상세 캐시를 모두 무효화하지 않도록 한다.
- DB 오류, 빈 결과, 404를 각각 테스트한다.

### P1. 인증 복구 흐름의 자동 회귀 검증 부재

#### 문제

초대 활성화, 만료 복구, 루트 리다이렉트가 세 개의 연속 수정 커밋으로 완성됐다. 현재 미커밋 변경은 `AuthRecoveryRedirect`를 루트 레이아웃에서 홈으로 이동해 적용 범위를 줄였고, 컴포넌트 내부 조건도 원래 `/`만 처리하므로 기능상 동등한 방향이다. 그러나 Supabase 프로젝트별 Redirect URL 설정, PKCE의 `code` 쿼리, 과거 implicit flow의 hash 오류, 만료/재사용 링크가 서로 다른 경로를 사용하며 이 이동을 보장하는 자동 테스트가 없다. 따라서 이후 레이아웃 또는 홈 구조 변경 시 같은 회귀가 다시 생길 수 있다.

#### 개선

- “신규 초대, 정상 복구, 만료, 재사용, 잘못된 코드, 루트로 돌아오는 구형 링크”를 인증 수용 테스트 행렬로 만든다.
- Redirect URL을 `/admin/activate`로 단일화하고 스테이징/운영 허용 목록을 운영 문서와 코드 검증에 함께 둔다.
- 구형 링크 지원을 종료하려면 종료 조건과 날짜를 정하고, 그 전에는 전역 클라이언트 컴포넌트 대신 최소 범위의 서버/Proxy 리다이렉트를 검토한다.
- URL의 오류 원문이나 토큰을 로그·Sentry에 저장하지 않는다.

### P1. 자동 품질 게이트와 DB 통합 테스트 부재

#### 문제

현재 `.github` 워크플로 파일이 없다. 로컬 스크립트는 있으나 PR이나 배포 전에 자동으로 실행된다는 보장이 없다. 단위 테스트는 애플리케이션 mock 중심이며 실제 PostgreSQL의 RLS, GRANT, 함수 권한, 트랜잭션을 검증하지 않는다. E2E는 공개 화면 이동 1건뿐이고 관리자 인증·CRUD·휴지통 복구·캐시 반영은 포함하지 않는다.

#### 개선

PR 필수 검사로 다음 순서를 구성한다.

1. 고정 pnpm/Node 버전으로 `pnpm install --frozen-lockfile`
2. `pnpm lint`, `pnpm typecheck`, `pnpm test`
3. 로컬 Supabase에 전체 마이그레이션 적용 및 RLS/RPC 계약 테스트
4. `pnpm build`
5. Chromium 설치 후 공개 smoke E2E와 관리자 핵심 흐름 E2E

보안상 최소 통합 테스트는 익명 사용자의 draft/trashed 조회 불가, 일반 인증 사용자의 관리자 CRUD 불가, 공개 RPC 직접 호출 불가, 관리자의 정상 CRUD, 휴지통 복구 상태 보존을 포함해야 한다.

### P2. Markdown 구현의 표준 호환성과 외부 리소스 정책

#### 문제

현재 렌더러는 React 텍스트 노드와 URL protocol allowlist를 사용하므로 `dangerouslySetInnerHTML` 기반 구현보다 안전한 출발점이다. `javascript:` 링크도 앵커로 렌더링하지 않는 테스트가 있다.

그러나 정규식 기반 파서는 중첩 괄호 URL, escape 문자, 중첩 inline mark, 복잡한 표와 목록 등 CommonMark/GFM 문법을 일관되게 처리하기 어렵다. 이미지에는 모든 `https:` URL을 허용하고 CSP도 `img-src https:`를 허용하므로 외부 추적 픽셀과 예기치 않은 호스트 요청이 가능하다. 편집 저장 형식, 레거시 Tiptap 변환, 표시 파서가 별도 규칙으로 발전하면 round-trip 손실도 생긴다.

#### 개선

- CommonMark/GFM parser와 명시적 sanitize schema를 사용하고 raw HTML은 기본 비활성화한다.
- 링크와 이미지 URL 정책을 하나의 유틸리티로 통합한다. 외부 이미지는 허용 도메인, 프록시, 또는 CMS 업로드 미디어만 허용하는 정책 중 하나를 선택한다.
- fixture 기반으로 “입력 Markdown → AST/렌더 결과 → plain text” 계약 테스트를 만든다.
- 레거시 Tiptap 문서는 일회성 마이그레이션 결과를 검증한 뒤 저장 형식을 단일화한다.

### P2. 관측성과 보안 헤더의 운영 수준 보완

#### 문제

현재 미커밋 `/api/health`는 프로세스가 응답한다는 liveness만 확인하며 DB 연결, 필수 테이블, 마이그레이션 상태는 확인하지 않는다. CSP는 `script-src 'unsafe-inline'`과 모든 HTTPS 이미지 호스트를 허용해 방어 강도가 제한된다. Sentry는 오류 수집을 추가했지만 배포 버전, 환경, 주요 CMS 상태 변경과 연결된 운영 기준은 문서화되지 않았다.

#### 개선

- `/api/health`는 빠르고 의존성 없는 liveness로 유지하고, 인증 또는 내부 접근으로 제한된 readiness에서 Supabase 읽기와 스키마 버전을 검사한다.
- Sentry에 release SHA와 environment를 부여하고, 로그인 제한 오류율, 공개 콘텐츠 fallback/조회 실패, CMS 부분 실패를 별도 태그와 경보 기준으로 관리한다.
- 가능하면 외부 폰트를 자체 호스팅해 CSP 범위를 줄인다. 이후 nonce 기반 script CSP를 적용하되 Next.js 렌더링 방식과 캐시 성능 영향을 함께 측정한다.
- 미디어 업로드는 브라우저가 보낸 MIME 값뿐 아니라 파일 signature/디코딩 결과를 확인하고, 공개 버킷을 유지한다면 draft·orphan 파일도 URL을 아는 사용자가 읽을 수 있다는 정책을 명시한다.

### P2. 변경 단위와 저장소 위생

#### 문제

초기 릴리스와 현재 작업 트리 모두 여러 관심사가 큰 단위로 묶여 있다. 이런 구조에서는 보안 수정만 되돌리거나 캐시 변경만 비교하기 어렵다.

#### 개선

다음 순서처럼 배포 가능하고 독립 검증 가능한 단위로 커밋한다.

1. 의존성 버전 고정
2. 브랜드/콘텐츠/디자인
3. SEO와 정적 메타데이터
4. 미디어 모델과 CMS 입력
5. 공개 조회 캐시와 무효화
6. Sentry와 health endpoint
7. 보안 헤더
8. 각 변경에 대응하는 테스트와 운영 문서

커밋 전 `git diff --check`, 비밀값 포함 여부와 생성 파일 위치를 확인한다. 마이그레이션과 애플리케이션 변경은 배포 순서를 커밋 또는 운영 문서에 명시한다.

## 7. 우선순위별 실행 계획

### 1단계: 즉시 처리

- 로그인 제한 RPC의 공개 실행 권한을 회수하고 서버 전용 제한 경계를 만든다.
- 운영에서 데모 fallback을 차단하고 오류/빈 결과/404를 분리한다.
- 현재 큰 작업 트리를 관심사별 커밋으로 분리한다.

### 2단계: 데이터 정합성

- CMS 저장, 태그/미디어 관계, 감사 로그, 순서 변경을 트랜잭션 RPC로 이동한다.
- 적용된 마이그레이션을 수정하지 않는 규칙과 보정 마이그레이션을 도입한다.
- 생성 DB 타입과 실제 스키마의 차이를 CI에서 검사한다.

### 3단계: 회귀 방지

- CI에 lint, typecheck, unit, migration/RLS integration, build, E2E를 연결한다.
- 인증 복구 테스트 행렬과 관리자 CMS 핵심 E2E를 추가한다.
- Playwright 브라우저 설치를 CI bootstrap에 포함한다.

### 4단계: 구조 현대화

- Next.js 16의 Cache Components 도입 여부를 결정하고 `unstable_cache`를 `use cache`/`cacheTag` 방식으로 전환한다.
- Markdown 표준 parser와 sanitize 정책을 도입한다.
- readiness, Sentry release/alert, 강화된 CSP와 미디어 검증을 운영 기준에 포함한다.
