## 2. 측정 방법과 한계

- 도구: Playwright(Chromium)로 운영 사이트 8개 경로를 열어 FCP·LCP·CLS·긴 작업 시간과 전송량을 쟀다. 원자료는 로컬 `tmp/perf-audit-2026-11-10/`에 있다(저장소에는 올리지 않는다).
- 모바일 조건: 390×844, CPU 4배 감속. 네트워크 감속은 첫 측정에서 적용되지 않았다. 다운로드 속도만 1.6Mbps로 제한한 두 번째 측정을 따로 적었다.
- 측정 위치: 춘천의 Oracle 서버. 실제 방문자의 통신망과 기기에서 잰 값이 아니다.
- 챗봇: 운영 사이트에 실제 질문 4건을 보냈다. **챗봇 모델이 이 측정 서버에서 함께 돌기 때문에**(§3 PF01), 측정용 브라우저가 쓴 CPU와 메모리가 결과에 영향을 줬을 수 있다. 특히 첫 질문의 58초는 그 영향을 포함한다.
- 접근성: axe-core로 6개 경로를 두 테마에서 검사했다. 자동 검사만 했다.

### PF01. 챗봇 응답이 느리다 — 가장 큰 문제

실제 질문 4건의 경과 시간(질문을 보낸 뒤 초):

| 질문 | 응답 시작 | 근거 도착 | 첫 글자 | 완료 |
| --- | ---: | ---: | ---: | ---: |
| 추천 질문 A (쉰 뒤 첫 요청) | 3.0 | 10.1 | **42.4** | 57.7 |
| 추천 질문 B | 1.8 | 2.6 | 2.7 | 10.3 |
| 추천 질문 A 반복 | 1.9 | 2.7 | 3.0 | 17.2 |
| 처음 받는 질문 | 1.9 | 2.4 | **11.8** | 19.4 |

읽는 법:

- **응답 시작까지 1.8–3.0초**는 모델과 무관한 대기다. Vercel 함수가 미국 동부(`iad1`)에서 돌고, Supabase와 챗봇 서버는 아시아에 있다. 중계 함수는 상태 조회 → 사용량 제한 → 챗봇 서버 연결을 차례로 하므로 태평양을 세 번 왕복한다.
- **같은 질문을 다시 받으면** 프롬프트 캐시 덕분에 근거 도착 0.1–0.3초 뒤에 첫 글자가 나온다. 질문 B가 빨랐던 것은 추천 질문이라 이전 캐시가 남아 있었기 때문으로 보인다.
- **처음 받는 질문**은 근거 문서를 새로 읽느라 약 9초가 더 걸린다. 6초 안내("로컬 AI로 답변을 만들고 있어요")가 거의 매번 뜬다.
- **오래 쉰 뒤 첫 질문**은 검색 7초, 프롬프트 처리 32초가 걸렸다. 원인은 확인하지 못했다. 모델 메모리가 디스크로 밀려났다가 다시 올라오는 시간일 가능성이 있다.
- 생성 속도는 초당 약 8.5토큰이다. 2코어 CPU의 한계이고, [10-19 최적화 기록](../operations/gemma-e2b-optimization-2026-10-19.md)에서 설정으로는 더 줄이지 못한다고 확인했다.

개선 방향(효과가 큰 순서):

1. **추천 질문 답변을 미리 만들어 둔다.** 홈 추천 질문 4개와 사례별 질문 12개는 문구가 고정이다. 인덱스가 바뀔 때마다 답변과 근거를 만들어 저장하고, 같은 질문이 오면 저장한 답을 스트리밍하듯 보여준다. 방문자가 가장 자주 누르는 경로가 1초 안으로 줄어든다.
2. **Vercel 함수 리전을 서울(`icn1`)로 옮긴다.** `vercel.json`에 리전을 지정한다. 챗봇 응답 시작이 1.5–2.5초 빨라지고, `/api/chat/status`(현재 0.9–1.25초), 관리자 저장, 로그인도 함께 빨라진다. Hobby 요금제에서 리전 변경이 되는지는 적용할 때 확인한다.
3. **쉰 뒤의 첫 질문을 없앤다.** 모델 서버에 `--mlock`을 주고, 몇 분마다 짧은 요청으로 검색 모델과 생성 모델을 깨워 두는 타이머를 둔다. 적용 전에 "쉰 뒤 첫 요청"을 따로 재서 원인을 확인한다.
4. **중계 함수의 조회를 줄인다.** 상태 조회와 사용량 제한을 동시에 보내고, 상태는 함수 메모리에 10–15초 캐시한다.
5. **개발 작업과 분리한다.** OP06 참고.

### PF02. Sentry가 꺼진 채 실려 있다

- Vercel 운영 환경 변수에 `NEXT_PUBLIC_SENTRY_DSN`이 없다. 그래서 Sentry는 초기화만 되고 아무것도 보내지 않는다.
- 그런데 SDK는 모든 페이지에 실린다. 가장 큰 JS 파일(압축 133KB, 원본 428KB)이 Sentry이고, 전체 JS 270KB의 절반이다. 모바일 긴 작업 430–830ms의 일부도 이 파일의 파싱이다.
- 운영 오류도 수집되지 않는다. 코드 곳곳의 `Sentry.captureException`이 실제로는 아무 일도 하지 않는다.

둘 중 하나를 정한다. 오류를 볼 생각이면 DSN을 넣고 클라이언트 쪽은 추적 기능을 뺀 최소 구성으로 줄인다. 안 쓸 거면 클라이언트 초기화를 빼고 서버 쪽만 남긴다.

### PF03. `/blog`에서 화면이 밀린다

- `BlogBrowser`가 `useSearchParams`를 써서 `Suspense`로 감싸져 있다. 처음에는 높이 20px짜리 "글 목록을 불러오는 중…"이 나오고, 곧 330px 넘는 목록으로 바뀌면서 푸터가 밀린다.
- 측정: 한 번의 이동이 CLS 0.408(모바일), 0.207(데스크톱)을 만든다.

페이지에서 `searchParams`를 받아 `BlogBrowser`에 초깃값으로 넘기면 서버에서 목록을 그릴 수 있다. 그게 어렵다면 대기 화면을 실제 목록과 같은 높이의 뼈대로 바꾼다.

### PF05. 글꼴이 전송량의 절반이고 캐시 설정이 없다

- 페이지마다 Pretendard 조각 13–15개, 330–390KB를 받는다.
- `public/` 아래 파일(글꼴, 글꼴 CSS, 근거 이미지, `og.png`)의 응답이 모두 `cache-control: public, max-age=0, must-revalidate`다. 다시 방문할 때마다 파일마다 서버에 확인 요청을 보낸다.
- 글꼴 CSS(압축 13KB, `@font-face` 92개)는 별도 요청이고 렌더링을 막는다.

개선: `next.config.ts`의 `headers()`에 `/assets/fonts/*`는 1년, `/assets/images/*`는 30일 캐시를 준다. 첫 화면에 쓰는 한글 조각 2–3개는 `preload`한다.

## 4. 방문자 편의

### UX01. 모바일 사례 페이지에서 본문이 너무 멀다

- 연세대 상세(390px): 전체 9,122px 중 근거 섹션이 3,507px다. 본문은 4,732px에서 시작한다. 화면 다섯 장 반을 내려야 한다.
- 목차는 본문 제목만 담고 있어 근거 섹션을 건너뛸 방법이 없다.

개선: 모바일에서는 사진과 캡처를 가로로 넘기는 한 줄로 바꾸고, 차트의 표는 접어 둔다. 히어로 아래에 "근거 자료 / 본문" 바로가기를 둔다.

### UX02. 챗봇이 근거 섹션 내용을 모른다

- 근거 섹션은 `data/portfolio/evidence.json`에서 그리고, 챗봇은 DB의 본문만 색인한다.
- 그래서 "매뉴얼은 몇 종 만들었나요?"나 "저장 용량이 얼마나 줄었나요?" 같은 질문에 화면에 있는 숫자로 답하지 못한다.

개선: 게시할 때 근거 수치와 일정을 본문 색인용 텍스트에 함께 넣는다(OP04의 게시 스크립트에서 처리).

### UX03. 채용 담당자가 가져갈 것이 없다

- 이력서 내려받기가 없다.
- GitHub, LinkedIn 같은 외부 프로필 링크가 없다. 소개 페이지 본문의 링크는 사례 2건뿐이다.
- 연락 수단은 메일 주소(열기, 복사)뿐이다.

개선: 이력서 PDF와 외부 프로필 링크를 소개·연락처·푸터에 둔다. 자료는 사용자가 준다.

### UX04. 라이트 테마에서 작은 글자가 흐리다

- 다크 테마는 6개 경로 모두 대비 문제가 없다.
- 라이트 테마는 모든 경로에서 걸린다. 보조 글자색 `--muted`(`#6d819a`)의 대비가 3.5–4.0:1이다(기준 4.5:1). 연세대 상세에서 30곳, 다른 경로에서 5–11곳이다. 10-14에 추가한 근거 섹션의 쪽수·출처 글자도 포함된다.

개선: 라이트 테마의 `--muted`를 `#5a6e87`로 바꾼다. 흰색부터 가장 어두운 라이트 표면까지 4.58–5.23:1이 나온다. 토큰 한 줄 수정이다.

## 5. 운영 편의

### OP01. GitHub와 운영 사이트가 따로 논다

- `origin/main`은 8월 6일 커밋(`cf1482e`)이다. 로컬 브랜치는 22개 커밋 앞서 있고 한 번도 올라가지 않았다. 이 서버에 GitHub 인증이 없어서다.
- 작업 트리에 커밋하지 않은 변경이 있다(수정 10개, 새 항목 7개). 그중 코드 변경(챗봇 모델명 표시, readiness, `.vercelignore` 등)은 11-03 배포에 이미 들어갔다. 로드맵의 "배포는 커밋된 상태에서만 한다"와 어긋나고, 09-24에 정리했던 상황이 다시 생겼다.
- 그 결과 CI는 8월 이후 돌지 않았고, 운영 사이트를 코드로 되돌릴 기준점이 없다.

개선: 이 저장소 전용 배포 키(SSH)를 만들어 GitHub에 등록하고 push한다. 밀린 변경을 작업 단위로 커밋한다.

### OP02. 배포가 수동 4단계다

지금 절차: `git archive`로 내보내기 → `.vercel/project.json` 복사 → `vercel deploy --prod` → 주요 경로 확인. 순서를 기억해야 하고, 작업 트리가 더러워도 막지 않는다.

개선: `scripts/deploy-production.sh` 하나로 묶는다. 커밋되지 않은 변경이 있으면 멈추고, 배포 뒤 주요 경로와 readiness를 확인한다. OP01이 풀리면 Vercel의 GitHub 연동으로 바꿔 push가 곧 배포가 되게 한다.

### OP03. 운영 오류를 볼 방법이 없다

PF02와 같은 원인이다. Sentry DSN이 없어 운영 오류가 어디에도 남지 않는다. 지금은 방문자가 알려 주거나 Vercel 로그를 직접 열어야 안다.

### OP04. 프로젝트 1건을 게시하려면 다섯 군데를 고친다

| 내용 | 위치 | 반영 방법 |
| --- | --- | --- |
| 본문, 요약, 기간, 태그 | Supabase DB | SQL 직접 실행 |
| 카드 도식, 수치, 역할 | `data/portfolio/presentation.json` | 배포 |
| 근거 섹션 | `data/portfolio/evidence.json` | 배포 |
| 홈 성과 줄, 추천 질문 | `data/content/home.json` | 배포 |
| 근거 이미지 | `scripts/build-portfolio-evidence-assets.py` | 실행 후 배포 |

관리자 화면에서 고칠 수 있는 것은 첫 줄뿐이다.

개선(단계별):

1. **게시 스크립트.** `data/portfolio/manifest.json`과 본문 Markdown을 읽어 DB에 반영하고(기존 `save_portfolio_atomic` RPC 사용), 근거 수치를 색인용 텍스트에 넣고, 재색인을 요청한다. SQL을 손으로 쓰지 않게 된다.
2. **도식·수치를 DB로.** 로드맵 N31대로 프로젝트 폼에서 고르게 한다.

### OP05. 관리자 화면의 남은 결함과 누락

로드맵 항목이 그대로 남아 있다. 코드에서 다시 확인했다.

- 데이터가 틀어질 수 있는 결함 3건: V01(발행 실패에도 상태가 "발행"으로 바뀜), V02(신규 저장 뒤 실패하면 ID를 잃음), N01(SEO 제목이 옛 제목으로 고정됨)
- 누락 기능: 카테고리 관리, 외부 링크 편집, slug 자동 제안, 복제·영구 삭제, 목록 검색, 실제 화면 미리보기(N06–N12, E07)

### OP06. 개발과 운영 챗봇이 같은 2코어 서버를 쓴다

- 챗봇 모델 서버, RAG API, 색인 워커가 이 서버에서 돈다. 같은 서버에서 VS Code, 빌드, 테스트, 브라우저 측정도 돈다.
- 11-03 기록에 "로컬 웹 빌드와 겹친 검색 timeout 1건"이 있다. 개발 작업을 하는 동안 방문자의 챗봇이 느려지거나 실패한다.
- `.next`가 2.9GB, `tmp/`가 33MB다.

개선: 빌드는 Vercel 원격 빌드에 맡기고 로컬 `pnpm build`는 꼭 필요할 때만 한다. 무거운 개발 명령은 낮은 우선순위(`nice`, `systemd-run -p CPUWeight=20`)로 돌린다. 모델 서비스에는 `CPUWeight`를 높게 준다. `.next`는 주기적으로 지운다.
