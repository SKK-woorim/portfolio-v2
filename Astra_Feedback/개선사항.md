# 현재 포트폴리오 결과물 정밀 검토 및 개선사항

작성: 2026-09-11 / 최초 화면 수집: 2026-09-09 / 기준 커밋: `d1c63fa`

이 문서는 현재 저장소의 코드, 연결된 Supabase의 공개 콘텐츠 조회 결과, 로컬에서 실행한 실제 화면을 함께 검토한 결과다. 디자인 취향에 따른 제안과 재현된 기능 결함을 구분했다. 개선을 구현한 문서가 아니라, 현재 결과물에 무엇이 부족하고 어떤 기준으로 수정해야 하는지 정리한 감사 보고서다.

## 1. 핵심 판단

시각적 방향과 기본 구조는 갖춰져 있다. 네이비·블루 테마, 반응형 메뉴, 공개 콘텐츠와 관리자 영역의 분리, Markdown 편집, 이미지 최적화, 챗봇 스트리밍, 테스트와 운영 문서가 이미 존재한다. 전면 재제작보다는 **콘텐츠 조회 정상화 → 편집 데이터 보존 → 접근성과 탐색 복구 → 실제 성과를 보여주는 콘텐츠 보강** 순서가 적절하다.

가장 큰 문제는 외관보다 기능의 신뢰성이다. **발행된 블로그 글이 실제로 3개 있는데도 블로그 화면은 0개를 표시하고, 기존 글 주소는 404를 반환한다.** 동시에 readiness는 정상으로 응답하고 기존 테스트도 통과한다. 따라서 현재의 “빌드 성공·테스트 성공”만으로 방문자 경험이 정상이라고 판단할 수 없다.

디자인 측면에서는 첫 화면이 “안녕하세요. / 송경근입니다.”에 머물고, 실제 프로젝트 이미지·공개 증빙 링크가 없으며, 사례 설명이 짧아 엔지니어로서의 판단과 기여를 평가하기 어렵다. 장식적인 기술 이미지와 넉넉한 여백에 비해 검증 가능한 정보의 비중이 낮다.

### 우선순위와 근거 표기

- **P1:** 핵심 기능·데이터 보존·출시 판단을 해치는 문제. 관련 기능을 신뢰하기 전에 수정한다.
- **P2:** 공개 품질과 사용성을 직접 떨어뜨리는 문제. 다음 개선 작업에 포함한다.
- **P3:** 콘텐츠 확장, 일관성, 운영 효율을 위한 후속 개선.
- **[실행 확인]:** 브라우저·공개 조회·로컬 재현으로 확인했다.
- **[코드 확인]:** 구현과 흐름으로 확인했다. 외부 서비스 변경을 수반하는 전체 운영 시나리오는 실행하지 않았다.
- **[설계 제안]:** 방문 목적과 현재 화면을 바탕으로 한 디자인·콘텐츠 판단이다.
- **[조건부]:** 특정 사용 조건에서의 위험이며, 현재 운영 장애가 발생했다고 단정하지 않는다.

## 2. 조사 범위와 검증 결과

### 확인한 범위

- 공개 홈, 소개, 포트폴리오 목록, 프로젝트 상세, 블로그 목록, 블로그 상세 오류, 연락처, 관리자 로그인 화면.
- 1440px 데스크톱의 라이트·다크 테마, 390px 모바일, 320px 좁은 화면. 최초 24개 페이지·화면 조합을 수집하고 문제 항목을 재검증했다.
- 메뉴·테마·검색·문의 연결·챗봇 비활성 상태·챗봇 내부 링크·키보드 포커스.
- Next.js 16.3.0 / React 19.2.8 코드, 관리자 폼, 콘텐츠 저장·조회, 미디어, 메타데이터, 캐시, Python RAG API·worker·evaluation, SQL migration, GitHub Actions, 운영 문서.
- Supabase는 공개 키로 `published` 콘텐츠를 읽어 조회 계약을 확인했다. 관리자 로그인·실제 저장·발행·삭제·마이그레이션 실행은 하지 않았다.

Python 기존 `.venv`에는 pytest가 없어 별도 임시 환경을 사용했다. 테스트는 해당 서비스 디렉터리에서 실행했다. 개발 서버의 화면 캡처에 보이는 Next.js 개발 도구 아이콘은 제품 결함으로 취급하지 않았다.

**범위의 한계:** 실제 사용자 인터뷰, Safari/Firefox와 실제 iOS 키보드, 스크린리더 실기기, 운영 도메인의 배포 상태·로그·접근 통제, 실제 모델의 답변 품질, DB 복구 훈련은 확인하지 않았다. 아래 수치는 로컬 측정이며 운영 Core Web Vitals나 실제 서비스 품질 점수로 해석하면 안 된다. 9월 9일 홈에 보였던 글 3개와 이후 빈 목록의 차이는 기록하되, 최종 판단은 9월 11일 재조회와 프로덕션 실행 결과를 기준으로 한다.

## 3. 디자인·콘텐츠 관점

### D01. 첫 화면이 전문성과 차별점을 충분히 전달하지 못함 — P2 [실행 확인·설계 제안]

**근거:** `src/app/(site)/page.tsx:35`, `src/lib/content/repository.ts:141`. 현재 공개 프로필의 메인 제목은 “안녕하세요.”, 소개 문구는 “송경근입니다.”다. 직무는 작은 상단 문구에만 있고 기술 태그가 그 아래 나열된다. [현재 첫 화면](screenshots/home-light.png)

**영향:** 처음 방문한 사람이 어떤 문제를 해결하는 사람인지, 어떤 경험 때문에 더 살펴봐야 하는지 빠르게 파악하기 어렵다. 이름·인사말이 가장 큰 시각적 공간을 차지하는 동안 실제 전문성은 아래로 밀린다. 푸터에서도 같은 짧은 인사말을 반복한다.

**개선:** 큰 제목을 역할과 해결하는 문제 중심으로 바꾸고, 본문에 다루는 데이터·수행 범위·관련 사례를 구체적으로 적는다. 예를 들어 확인된 경험에 근거해 “문서와 데이터를 연결하는 AI Agent·RAG 엔지니어” 같은 방향을 검토할 수 있다. 인사말은 짧은 보조 문구로 옮긴다. 수치나 경력은 근거가 있는 것만 사용한다.

**완료 기준:** 첫 화면에서 이름, 전문 분야, 대표적인 수행 범위, 다음 행동을 이해할 수 있어야 한다. 핵심 내용을 알려면 태그 10개를 해석해야 하는 구성을 피한다.

### D02. 프로젝트 사례에서 개인 기여와 검증 가능한 결과가 부족함 — P2 [실행 확인·설계 제안]

**근거:** `src/app/(site)/portfolio/[slug]/page.tsx:58`, 공개 프로젝트 4개의 본문 및 관계 데이터. AI 워크플로우는 세 문단으로 업무를 요약하고, 다른 사례도 짧은 요약 중심이다. 모든 `portfolio_links`가 비어 있다. 지하수 예측 사례에는 “RMSE 0.054”가 있지만 단위·정규화 여부·예측 구간·비교 기준이 설명되어 있지 않다. [공개 콘텐츠 근거](evidence/public-query-evidence.json)

**영향:** 기술을 사용했다는 사실은 알 수 있지만 무엇을 직접 설계했는지, 어떤 제약에서 어떤 선택을 했는지, 결과가 어느 정도 좋은지 판단하기 어렵다. 수상·논문 언급도 독자가 확인할 수 있는 경로가 없다.

**개선:** 각 사례를 문제·제약 → 역할과 팀 구성 → 설계 및 대안 → 구현 → 검증 결과 → 한계·회고 순으로 구성한다. RMSE는 평가 데이터, 기준 모델, 단위, 측정 조건과 함께 적는다. 공개 가능한 논문·수상 안내·저장소·시연 자료를 연결하고 비공개 업무는 익명화한 구조도와 본인 기여 범위로 설명한다.

**완료 기준:** 대표 사례마다 개인 기여를 구분할 수 있고, 주요 주장에 대응하는 근거 또는 공개 제한 사유가 있어야 한다. 결과 숫자는 비교·재현 조건 없이 단독으로 배치하지 않는다.

### D03. 프로젝트 썸네일이 실제 결과물을 구별해주지 못함 — P2 [실행 확인·설계 제안]

**근거:** `src/components/project-visual.tsx:28`. 공개 프로젝트 4개 모두 대표 미디어 관계가 없어 같은 형태의 직사각형·막대 장식이 색상만 달리 표시된다.

**영향:** AI 워크플로우, 수위 예측, 객체 탐지, 3D 생성이라는 서로 다른 프로젝트가 비슷하게 보인다. 장식이 로딩 skeleton처럼 보일 수 있으며, 화면만 보고 프로젝트를 기억하기 어렵다.

**개선:** 업무 흐름도, 예측 결과 그래프, 탐지 결과, 3D 출력물처럼 각 프로젝트의 핵심 결과를 보여주는 자료로 교체한다. 이미지를 공개할 수 없는 사례에는 프로젝트명을 포함한 전용 도식과 짧은 결과 요약을 제공한다. 무관한 장식 이미지를 추가해 빈 곳만 채우는 방식은 피한다.

**완료 기준:** 썸네일만 보아도 서로 다른 사례를 구분할 수 있고, 이미지가 상세 내용의 핵심 주장과 연결되어야 한다.

### D04. 홈에서 실제 작업물을 만나기까지 스크롤이 너무 김 — P2 [실행 확인·설계 제안]

**근거:** `src/app/(site)/page.tsx:31`, `src/app/globals.css:38`. 390×844 화면에서 “AI와 데이터로 해결한 문제들” 제목은 문서 상단 약 1,936px, 첫 프로젝트 제목은 약 2,410px 지점에 위치했다. 히어로 뒤에 큰 작업 원칙 섹션이 먼저 배치된다.

**영향:** 채용 담당자나 협업 상대가 보고 싶은 실적에 도달하기 전에 일반적인 소개·원칙을 오래 읽어야 한다. 특히 모바일에서 핵심 정보가 두세 화면 아래에 있다.

**개선:** 대표 프로젝트를 히어로 다음으로 올리거나 첫 화면에 대표 성과 한 개를 함께 노출한다. 작업 원칙은 사례에서 실제로 적용한 방식으로 설명하거나 더 짧게 요약한다. 섹션별 중요도와 콘텐츠 분량에 따라 여백을 달리하고 모바일 히어로 높이를 재조정한다.

**완료 기준:** 모바일에서 짧은 한 번의 스크롤로 대표 사례의 제목과 의미를 확인할 수 있어야 한다. 여백 축소로 본문 가독성을 해치지 않는지도 함께 확인한다.

### D05. 소개 페이지에 경력·역할·숙련 근거가 부족함 — P2 [실행 확인·설계 제안]

**근거:** `src/app/(site)/about/page.tsx:17`. 현재 구성은 일반적인 협업 문구, 강점 세 개, 기술 태그 목록이다. 경력 흐름, 활동 기간, 맡았던 역할, 외부 프로필·이력서로 이어지는 구체적인 정보가 없다. 현재 프로필의 외부 링크도 공개 화면에 나타나지 않는다.

**영향:** 기술 이름을 아는 것과 해당 기술로 실무 결과를 만든 것을 구분하기 어렵다. 상세 프로젝트를 읽기 전에 필요한 기본 배경 정보가 부족하다.

**완료 기준:** “언제, 어떤 역할로, 무엇을 해봤는가”와 기술별 실제 경험을 소개 페이지에서 파악할 수 있어야 한다.

## 4. 방문자·관리자 사용 경험 관점

### U01. 검색 입력을 URL 상태에만 의존해 빠른 입력이 불안정 — P2 [개발 모드 실행 확인·운영 재현 범위 제한]

**근거:** `src/components/blog-browser.tsx:25,47,61`. 입력값은 `useSearchParams()`에서 읽고, 매 `onChange`마다 `router.replace()`를 실행한다. 개발 서버에서 hydration 완료 후 `rag workflow`를 입력했을 때 20ms 간격에서는 `w`, 100ms 간격에서는 `rw`만 남는 결과를 확인했다. 300ms 간격은 정상이다.

**검증 경계:** 프로덕션 빌드에서는 20ms·100ms 입력과 페이지 이동 응답 500ms 지연 조건 모두 정상 입력되었다. 따라서 운영 방문자에게 항상 발생하는 버그로 단정하지 않는다. 실제 한글 IME는 별도 검증이 필요하다. [프로덕션 지연 조건 확인](evidence/search-production-check.json)

**개선:** 입력의 즉시 표시 상태는 로컬 state로 유지하고 URL 동기화를 분리한다. 검색은 로컬 값으로 즉시 반영하고 URL은 짧게 debounce하거나 명시적인 제출로 갱신한다. 조합 입력 중에는 URL 갱신을 보류하고 뒤로 가기·외부 URL 진입과의 동기화 규칙도 정의한다.

**완료 기준:** 한글·영문 빠른 입력, 삭제, 붙여넣기, 조합 입력, URL 직접 진입, 뒤로 가기에서 입력과 검색 결과가 일치해야 한다. 개발 모드와 프로덕션 모드 모두 검사한다.

### U02. 320px에서 블로그 검색창이 오른쪽으로 잘림 — P1 [실행 확인]

**근거:** `src/components/blog-browser.tsx:59`. 프로덕션 320px 화면에서 input은 x=76, 폭=276px로 오른쪽 끝이 352px까지 나간다. 상위 그리드의 자동 최소 크기가 검색 줄의 intrinsic width를 유지하고 `.site-theme`의 `overflow: clip`이 이를 숨긴다. [재현 화면](screenshots/blog-320.png)

**영향:** 검색창과 필터 구획이 카드 밖으로 나가 일부 영역을 볼 수 없다. 문서 전체에 가로 스크롤이 없다는 검사만으로는 이 문제를 발견할 수 없다. 320 CSS px는 reflow 검토에서 중요한 조건이다. [W3C reflow 설명](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

**개선:** 상위 grid track을 `minmax(0, 1fr)`로 제한하거나 해당 grid item·label·검색 래퍼에 `min-width: 0`을 적용한다. input에도 실제 사용 가능한 폭에 맞는 축소 규칙을 준다. 전역 overflow로 덮어 가리는 방식으로 해결하지 않는다.

**완료 기준:** 320·360·390px와 확대 조건에서 검색창, 필터, 결과 안내가 모두 콘텐츠 영역 안에 들어와야 한다. `scrollWidth`뿐 아니라 요소 bounding box와 실제 화면을 검사한다.

### U03. 카드가 클릭 가능해 보이지만 작은 링크만 동작 — P2 [실행 확인]

**근거:** `src/components/project-card.tsx:10,25`, `src/components/post-card.tsx:11,27`. 카드 전체에 hover 이동·그림자가 있지만 제목과 이미지에는 링크가 없다. 모바일 프로젝트 “자세히 보기” 링크는 약 83×20px다. 글 카드 링크 이름도 모두 “읽기”다.

**영향:** 큰 이미지·제목을 눌러도 이동하지 않아 예측을 어긴다. 좁은 링크를 정확히 눌러야 하며 스크린리더 링크 목록에서는 목적지를 구분하기 어렵다.

**개선:** 제목을 기본 링크로 만들고 필요하다면 중첩 링크가 생기지 않도록 카드 전체 클릭 영역을 확장한다. 카드별 접근 가능한 링크 이름에 프로젝트·글 제목을 포함한다. 터치 동작은 44px 수준의 편안한 영역을 목표로 한다.

**완료 기준:** 제목·주요 시각 영역 클릭이 기대한 이동으로 이어지고 키보드 포커스가 명확해야 한다. 44px는 여기서 제안하는 사용성 목표다. WCAG 2.2 AA의 최소 target 기준은 24px와 예외 조건을 포함하므로 현재 20px 높이만으로 무조건 위반이라고 단정하지 않는다. [W3C target size 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### U04. 페이지 제목과 오류 화면의 문서 구조가 일관되지 않음 — P2 [실행 확인]

**근거:** `src/components/section-heading.tsx:15`는 항상 h2를 만든다. 이를 hero에 사용하는 `/about`, `/portfolio`, `/blog`에는 h1이 없다. `src/app/not-found.tsx:3`는 자체 main을 반환해 개발 모드에서 사이트 layout 안에 렌더링되는 글 상세 오류 화면에는 main이 중첩된다. 프로덕션의 직접 404 진입은 다른 렌더링 형태였으므로 중첩 문제는 진입 경로별로 확인해야 한다.

**영향:** 페이지의 대표 제목과 주요 landmark를 탐색하기 어렵다. 화면 스타일은 비슷해도 문서 구조는 달라진다.

**개선:** SectionHeading에 의미 수준을 지정하는 `as`/`level` 옵션을 주거나 PageHeading을 별도로 둔다. 오류 컴포넌트가 어느 layout 안에서 렌더링되는지 기준을 정해 main을 한 곳에서 소유한다. 본문 Markdown의 h1 처리 정책도 정한다.

**완료 기준:** 정상 페이지에는 의미 있는 대표 h1이 있고, 직접 방문·내부 이동·존재하지 않는 slug에서 main landmark가 중첩되지 않아야 한다. h1 누락을 즉시 검색 순위 하락으로 단정하는 대신 문서 구조 품질 문제로 관리한다.

### U05. 현재 메뉴가 시각적으로 구분되지 않음 — P2 [코드 확인]

**근거:** `src/components/site-header.tsx:57`. `aria-current`는 올바르게 지정하지만 현재 경로 여부가 class에는 반영되지 않는다. 모든 메뉴 링크가 같은 기본 스타일이다.

**영향:** 상세 페이지에 들어간 사용자가 현재 속한 섹션을 시각적으로 확인하기 어렵다. 접근성 속성 구현과 일반 사용자에게 보이는 상태가 분리되어 있다.

**개선:** 현재 메뉴에 색상 외에 밑줄·배경·굵기 등 안정적인 표시를 추가한다. 포트폴리오 상세에서는 포트폴리오, 글 상세에서는 블로그가 활성 상태를 유지하도록 한다.

**완료 기준:** desktop·mobile·양쪽 테마에서 활성 메뉴가 보이고 `aria-current`와 표시가 일치해야 한다.

### U06. 콘텐츠 없음·검색 결과 없음·조회 실패를 구분하지 못함 — P2 [실행 확인]

**개선:** 정상 빈 상태, 필터 불일치, 요청 실패를 별도 데이터 상태로 전달한다. 정상 빈 상태에는 발행 준비 안내나 대체 사례를 보여주고, 조회 실패에는 재시도·오류 안내를 제공한다. 홈 섹션은 적절한 fallback 또는 노출 생략 정책을 갖는다.

**완료 기준:** 세 상태가 서로 다른 설명과 행동을 제공해야 한다. 필터가 없는 경우 초기화 버튼을 해결책으로 제시하지 않는다. 데이터 처리 수정은 E02와 함께 한다.

## 5. 개발·데이터·성능 관점

### E01. posts–media 관계를 명시하지 않아 블로그 전체가 비정상 — P1 [실행 확인]

**근거:** `src/lib/content/repository.ts:233,258`. 목록과 상세 모두 `media(public_url, alt)`를 포함한다. `posts.cover_media_id`를 통한 대표 이미지 관계와 `post_media`를 통한 본문 이미지 관계가 함께 존재하므로 PostgREST가 어떤 관계인지 결정하지 못한다.

**재현 결과:** 같은 공개 권한으로 기본 posts 조회는 200·3개이고 현재 앱과 같은 관계 조회는 HTTP 300·`PGRST201`이다. 오류 메시지는 `more than one relationship was found for 'posts' and 'media'`다. 관계를 명시한 읽기 전용 조회는 다시 200·3개를 반환했다. [조회 근거](evidence/public-query-evidence.json)

**영향:** `/blog`는 0개, `/blog/rag-document-pipeline`는 404, RSS는 항목 없음, 사이트맵은 블로그 상세 주소 없음으로 재현되었다. 캐시가 남은 홈에서는 잠시 글 카드가 보일 수 있어 화면 간 불일치도 생긴다. [프로덕션 확인 결과](evidence/production-summary.json)

**개선:** 목록·상세에서 대표 이미지 관계를 명시한다. 현재 확인한 schema에서는 다음과 같은 선택이 가능하다.

```text
media:media!posts_cover_media_id_fkey(public_url, alt)
```

본문 이미지 관계는 별도 이름으로 조회한다. 수정 뒤 관련 콘텐츠 태그·페이지 캐시를 정상적으로 갱신하고 홈·목록·상세·RSS·사이트맵을 함께 확인한다. 관계가 여럿일 때 외래 키를 지정하는 방식은 공식 문서에서도 설명한다. [Supabase joins 문서](https://supabase.com/docs/guides/database/joins-and-nesting)

**완료 기준:** 대표 이미지 없음·있음·본문 이미지 포함의 세 경우를 실제 테스트 DB에서 읽을 수 있어야 한다. 발행 글 수, 상세 200, RSS item 수, 사이트맵의 글 URL이 같은 공개 데이터 집합과 일치해야 한다.

### E02. 조회 오류를 정상 데이터로 바꾸어 장시간 캐시 — P1 [코드 확인·실행 확인]

**근거:** `src/lib/content/repository.ts:167,193,218,239,264`. `unstable_cache` 내부에서 예외를 잡은 뒤 목록은 `[]`, 상세는 `undefined`, 프로필은 demoProfile을 반환한다. 재검증 주기는 3,600초다.

**영향:** 실패 결과가 호출 성공으로 취급되어 빈 목록·404·대체 프로필이 정상 결과처럼 캐시에 들어갈 수 있다. 장애가 끝나도 즉시 정상 콘텐츠로 돌아오지 않을 수 있으며 오류 UI도 실행되지 않는다. E01이 실제로 이 흐름을 거쳐 방문자에게 콘텐츠 부재로 보였다.

**개선:** 정상적으로 존재하지 않는 결과와 의존성 조회 실패를 구분한다. 실패는 캐시 함수 밖으로 전달하고, 성공했던 데이터 유지·재검증 재시도·오류 UI 정책을 명시한다. demoProfile은 명시적인 로컬 데모 모드와 설정되지 않은 초기 환경에 제한한다. 모든 공개 조회에는 합리적인 시간 제한도 둔다.

**완료 기준:** DB 오류를 주입했을 때 기존 글이 “삭제된 글”처럼 취급되지 않아야 한다. 복구 후 정상 데이터가 되돌아오고 실패 fallback이 성공 캐시를 오염시키지 않는지 확인한다.

### E03. CMS의 처리된 오류 응답 후 작성한 입력값이 되돌아감 — P1 [컴포넌트 실행 확인]

**근거:** `src/components/admin/post-form.tsx:20–35`, `portfolio-form.tsx:22–42`, `src/app/admin/actions.ts:198`. 폼은 `action={formAction}`을 사용하고 제목·slug·요약·태그 등은 `defaultValue` 기반이다. 서버는 검증 실패도 예외 대신 `{ error: ... }`를 반환한다.

**재현:** 실제 PostForm을 렌더링해 “기존 제목”을 “새로운 제목”, “기존 요약”을 “수정된 요약”으로 바꾼 뒤 저장 함수가 업무 오류를 반환하도록 했다. alert가 나타난 뒤 제목·요약이 기존 값으로 되돌아갔다. DB 쓰기는 실행하지 않았다. [확인용 테스트 결과](evidence/form-reproduction.log)

**영향:** slug 중복·동시 편집 충돌·검증 실패를 고치려다가 방금 작성한 메타데이터를 잃는다. 본문은 controlled state라 남을 수 있어 일부만 사라지는 더 혼란스러운 상태가 된다.

**개선:** 편집 폼 전체를 controlled 상태로 관리하거나 action 반환값에 제출 값을 포함해 다시 채운다. 성공·업무 오류·예외 상황마다 reset 정책을 명시한다. 단순히 오류를 throw하도록 바꾸어 입력 화면 전체를 오류 경계로 보내는 해결은 적절하지 않다. React의 form action은 정상 종료 시 uncontrolled 필드를 reset한다. [React form 문서](https://react.dev/reference/react-dom/components/form)

**완료 기준:** 신규·기존 글과 프로젝트의 검증 실패·중복·충돌·일시 저장 실패 뒤 모든 입력이 보존되어야 한다. 성공 후에도 계속 편집하는 폼이라면 저장된 값이 화면에 유지되어야 한다.

### E04. 즉시 발행 결과와 폼의 저장 상태가 분리됨 — P1 [컴포넌트 실행 확인·운영 경로 조건부]

**근거:** `src/components/admin/post-form.tsx:27`, `portfolio-form.tsx:39`, `src/app/admin/actions.ts:194,223`, `src/lib/validation/content.ts:145`. “즉시 발행”은 서버에서 status를 published로 바꾸지만 반환 상태에는 id·slug·updatedAt만 있다. select는 초기 props의 `defaultValue`를 사용한다.

**재현 및 경계:** 초안 PostForm에 발행 성공 응답과 새 버전을 반환했을 때 select는 draft로 남았다. 부모 Server Component가 즉시 새 published props를 공급하는 경우까지 포함한 실제 관리자 저장 흐름은 실행하지 않았다. 현재 컴포넌트는 자체적으로 상태 일치를 보장하지 않는다.

**영향:** 새 props 반영 없이 다음 “변경 사항 저장”이 실행되면 사용자는 본문만 수정하려 했는데 status=draft를 제출해 발행을 중단할 수 있다. 신규 생성 뒤 `/new` 상태를 계속 사용하는 흐름도 현재 저장 대상과 상태를 이해하기 어렵게 한다.

**개선:** 서버의 저장 결과에 확정된 status와 정규화된 폼 값을 포함하고 화면 상태를 함께 갱신한다. 신규 저장 뒤 편집 주소로 전환할지 정책을 정한다. 일반 저장과 상태 변경의 의미를 UI에서 분명히 한다.

**완료 기준:** 초안 작성 → 즉시 발행 → 본문 수정 → 일반 저장을 수행해도 published가 유지되어야 한다. 숨김·비공개 전환은 사용자가 선택한 경우에만 일어나야 한다.

### E05. Tailwind 계층 밖의 전역 reset이 유틸리티를 덮어씀 — P1 [실행 확인]

**근거:** `src/app/globals.css:30,32`. `a { color: inherit; text-decoration: none; }`와 form 요소의 `font: inherit`가 `@layer` 밖에 있다. Tailwind의 layer 내부 색상·글꼴 유틸리티보다 우선 적용된다. 실제 라이트 모드 선택 필터는 class에 `text-white`가 있어도 계산된 색이 `#0b1d35`다. 일부 CTA는 `!important`로 개별 보정하고 있다.

**영향:** 코드를 읽었을 때 예상한 색·글꼴과 실제 화면이 다르다. D09의 대비 문제 일부가 여기에서 발생하고 이후 UI에서도 같은 문제가 반복될 수 있다. 단순히 class를 더 추가해도 해결되지 않는다.

**개선:** reset을 `@layer base`에 배치하고 유틸리티가 의도대로 덮어쓸 수 있게 한다. 링크·버튼의 공통 역할은 component layer 또는 공통 컴포넌트로 정의한다. 기존 `!important` 보정은 필요한 이유를 검토한 뒤 정리한다.

**완료 기준:** 대표 링크·선택 필터·CTA·관리자 입력의 computed style이 선언한 variant와 일치해야 한다. 전역 변경 영향이 크므로 정상·hover·focus·disabled 상태를 양쪽 테마에서 회귀 검사한다. D09는 이 문제의 화면상 결과이며 별개의 중복 구현 작업으로 산정하지 않는다.

### E06. 임시 저장과 이탈 경고가 본문만 보호 — P2 [코드 확인]

**근거:** `src/components/markdown-editor.tsx:19,90,123,165`. LocalDraft는 markdown·저장 시각·baseUpdatedAt만 보관하고 dirty는 `markdown !== baseline`이다. 제목·요약·태그·분류·이미지·기간·발행 상태는 추적하지 않는다.

**영향:** 메타데이터만 변경하고 이동하면 경고가 없고 복원도 되지 않는다. 사용자는 임시 저장 안내를 보고 글 전체가 보호된다고 생각할 수 있다. 신규 글의 공통 `new` 키와 계정 구분 없는 키도 작성 세션의 의미가 불명확하다.

**개선:** 문서 단위 form state와 dirty 상태를 구성하고 복원 대상 필드를 명시한다. 문서 ID·사용자·작성 세션을 고려해 키를 설계한다. 충돌 시 서버 버전과 로컬 초안을 비교할 수 있게 하고 저장되지 않은 필드를 빠짐없이 표시한다.

**완료 기준:** 본문을 건드리지 않고 제목·태그·대표 이미지만 바꾼 경우에도 이탈 감지와 복원이 동작해야 한다. 계정 변경·여러 새 글 작성·서버 갱신 상황에서 잘못된 초안을 자동 적용하지 않아야 한다.

### E08. 포트폴리오 순서 변경의 접근성과 실패 복구 부족 — P2 [코드 확인]

### E10. 미디어 metadata를 렌더링에서 충분히 활용하지 못함 — P2 [코드 확인]

**근거:** `src/lib/content/repository.ts:85`, `src/lib/content/types.ts:24`, `src/components/markdown-content.tsx:62`. 서버 업로드는 폭·높이를 저장하지만 공개 ContentImage에는 src·alt만 있고 Markdown 이미지는 크기 예약 없는 일반 img다. `media.alt?.trim() || fallbackAlt`는 의도적인 빈 alt도 제목으로 덮어쓴다.

**영향:** 본문 이미지가 늦게 로드되면 읽던 위치가 움직일 수 있다. 장식용으로 설정한 대표 이미지가 보조 기술에는 중복 제목으로 읽힐 수 있다. 모든 이미지가 문제인 것은 아니며, 현재 cover의 Next Image fill과 고정 비율 영역은 이미 적용되어 있다.

**개선:** 관리형 미디어에는 폭·높이 또는 aspect ratio를 전달해 공간을 예약한다. 외부 이미지에도 가능한 범위에서 크기·fallback 정책을 둔다. alt의 “설정되지 않음”과 “장식용 빈 문자열”을 구분해 보존한다.

**완료 기준:** 느린 이미지 로딩에서도 본문 위치 이동이 최소화되어야 한다. 장식용은 `alt=""`, 의미 있는 이미지는 구체적인 설명이 실제 DOM에 반영되어야 한다.

### E11. 비공개 콘텐츠 상태와 public Storage 파일 접근은 별개 — P2 [코드 확인·보호 요구에 따른 조건부]

**근거:** `supabase/migrations/202608050001_initial_schema.sql:240`은 media 버킷을 public으로 만든다. 후속 migration은 공개 사용처에 대한 media 행 조회를 제한하지만 버킷을 private으로 바꾸지 않는다.

**영향:** DB에서 글을 비공개로 바꾸더라도 이미 알려진 public 이미지 URL의 접근이 함께 철회되는 구조는 아니다. 초안·비공개 첨부파일도 보호해야 한다면 현재 모델과 요구가 맞지 않는다. 이번 감사에서 비공개 파일 유출은 확인하거나 시도하지 않았다. [Supabase 버킷 접근 모델](https://supabase.com/docs/guides/storage/buckets/fundamentals)

**완료 기준:** staging에서 초안 이미지·발행 이미지·비공개 전환 후 알려진 URL 접근을 정책대로 검증한다. 글 상태 변경과 파일 접근 권한을 같은 의미로 안내하지 않는다.

### E12. 공유 메타데이터 fallback과 프로필 데이터 출처가 분산 — P2 [코드 확인]

**근거:** `src/app/(site)/portfolio/[slug]/page.tsx:25`, `src/app/(site)/blog/[slug]/page.tsx:27`는 cover가 없으면 `images: []`를 명시한다. root에는 기본 OG가 있으나 상세 메타데이터가 빈 이미지 배열로 덮어쓴다. root metadata, manifest, 글·프로젝트 JSON-LD 작성자 이름은 CMS 프로필과 별도로 하드코딩되어 있다.

**영향:** 현재처럼 대표 이미지가 없는 사례는 공유 이미지 fallback이 사라질 수 있다. CMS에서 이름·소개를 수정하면 화면과 검색·공유 정보가 서로 달라질 수 있다.

**개선:** 이미지가 없으면 검증된 기본 OG 또는 제목별 OG를 사용한다. 프로필·브랜드 metadata의 단일 데이터 출처를 정하되 서버 캐시와 build 환경을 고려한다. 생성된 HTML의 OG·Twitter·canonical·JSON-LD를 실제로 확인한다.

**완료 기준:** 대표 이미지 유무와 관계없이 공유 카드가 의도대로 구성되어야 한다. CMS의 공개 이름과 메타데이터 작성자가 일치하고 잘못된 slug는 정상 글 메타데이터를 상속하지 않아야 한다.

### E13. 자체 Markdown 파서의 지원 범위와 경계 사례가 불명확 — P2 [코드 확인]

**근거:** `src/components/markdown-content.tsx:49,58,111,133`. 링크·이미지는 정규식으로 첫 `)`까지 파싱하고 표는 단순 `|` 분리다. 예를 들어 괄호를 포함한 URL, escaped pipe가 있는 표, 일부 중첩 강조·긴 코드 fence에서 일반 Markdown 작성 기대와 차이가 날 수 있다.

**영향:** 관리자가 미리보기와 본문을 신뢰하기 어렵고 기술 문서에 자주 나오는 코드·표·링크에서 의미가 바뀔 수 있다. 기존 parser는 HTML 실행과 위험 URL을 제한하고 있으므로 교체 과정에서 이 보안을 잃으면 안 된다.

**개선:** 지원 문법을 명시하고 실제 사용 사례의 fixture를 만든다. 유지 비용에 따라 검증된 Markdown AST parser를 도입하거나 현재 parser의 지원 범위를 좁혀 명확히 한다. 렌더링·목차·본문 텍스트 추출이 같은 구조를 기반으로 동작하도록 한다.

**완료 기준:** 괄호 URL, escaped pipe, 중첩 목록, inline code, 이미지 alt, 중복 제목, 코드 안의 마크업 문자가 내용 손실 없이 처리되어야 한다. 위험 URL·HTML에 대한 기존 보호도 계속 통과해야 한다.

### E14. 답변 길이 제한 종료를 정상 완료로 표시 — P2 [코드 확인]

**근거:** `services/rag-api/app/service.py:201–215`는 `finishReason`을 stop·length·cancelled로 전달한다. `src/components/chatbot/use-chat-stream.ts:214–229`는 토큰을 받았으면 done을 모두 complete로 처리하고 완료 콜백에는 종료 사유를 전달하지 않는다.

**영향:** 출력 길이 제한으로 문장이 끊겨도 완성된 답변처럼 표시될 수 있다. 취소·부분 답변·정상 완료를 구분하지 못해 사용자가 근거가 빠진 답변을 완성본으로 오해할 수 있다.

**개선:** 종료 사유를 타입과 메시지 상태까지 전달한다. length에는 부분 답변 안내와 질문을 좁혀 다시 묻기 등의 회복 행동을 제공한다. 모델이 반환한 출처 표기와 실제 sources의 관계도 검증한다.

**완료 기준:** stop·length·cancelled·토큰 없는 done을 각각 모킹했을 때 올바른 상태와 안내가 나타나야 한다.

### E15. 성능의 실측 기준과 초기 전송 예산이 부족함 — P3 [일부 실행 확인·설계 제안]

### E16. 유지보수용 파일 경계와 운영 문서 안내가 어긋남 — P3 [코드 확인]

**완료 기준:** 임시 검증 자료가 생겨도 제품 lint/typecheck 결과가 바뀌지 않아야 한다. 문서의 초기 실행 설명과 실제 공개 화면이 일치하고 주요 변경을 한 줄 전체 diff 없이 검토할 수 있어야 한다.

### E17. 데이터베이스 타입과 실제 조회 계약의 연결이 약함 — P2 [코드 확인]

**완료 기준:** 관계 변경·필드 삭제·RPC 반환 형태 변경이 CI에서 탐지되며, 타입 캐스팅으로 오류가 감춰지지 않아야 한다. 생성 타입만으로 실제 PostgREST 관계 검사를 대체하지 않는다.

### E18. CSP의 inline script 허용을 장기적으로 줄일 여지 — P3 [코드 확인·방어 강화 제안]

**근거:** `next.config.ts:6`은 production에서도 `script-src 'self' 'unsafe-inline'`을 사용하고 root layout의 테마 초기화가 inline script다. 이미 object/frame 차단, frame-ancestors, 각종 보안 헤더는 구현되어 있다.

**완료 기준:** CSP 강화 후 직접 진입·내부 이동·테마·CMS·오류 수집이 동작해야 한다. 실제 보안 사고와 구분해 단계적인 방어 개선으로 관리한다.

### O04. RAG용 텍스트 추출 과정에서 본문의 의미 구조가 사라짐 — P2 [코드 확인]

**근거:** `src/lib/content/markdown.ts:96`의 `markdownToPlainText()`는 코드 블록을 제거하고 제목 기호·개행·연속 공백을 평탄화한다. `worker/source_loader.py:90,124`는 이 `content_text`를 읽고 normalization은 고정된 “본문” 헤더를 붙인다.

**영향:** 원문에 섹션별 판단·실험·결과가 있어도 RAG 입력에는 주제 경계가 줄어든다. 코드나 설정 예시 안에만 있는 중요한 사실은 아예 검색 근거에서 사라질 수 있다. 콘텐츠가 짧은 현재보다 기술 글을 확장했을 때 문제가 커진다.

**완료 기준:** 같은 글의 다른 섹션을 묻는 질문이 적절한 섹션을 검색해야 한다. 추출 전후 사실·제목·수치가 보존되는지 fixture와 검색 평가로 확인한다.

### O05. 백엔드의 일시 장애 후 자동 복구가 중단될 수 있음 — P2 [코드 확인·조건부]

**근거 1:** `services/rag-api/deploy/systemd/portfolio-rag-api.service:16`은 LLM health를 최대 3초 동안 한 번 확인한다. LLM은 `Type=simple`로 시작하고 API의 재시작은 10초 간격, 5분 내 4회 제한이다. 모델이 프로세스 시작 뒤 오랫동안 준비되지 않으면 제한을 소진할 수 있다. `TimeoutStartSec=180`만으로 반복 readiness 확인이 생기지는 않는다.

**근거 2:** `worker/sync.py:47`의 claim은 try 바깥에 있고 오류 처리 중 `repository.fail()`도 실패할 수 있다. `worker/main.py:44`의 루프에는 해당 의존성 예외에 대한 바깥 복구가 없다. worker unit에도 같은 시작 횟수 제한이 있다.

**영향:** 느린 cold start 또는 잠깐의 DB·네트워크 장애가 수동 재시작이 필요한 장기 중단으로 이어질 수 있다. 실제 운영 서버를 재시작하거나 장애를 주입하지 않았으므로 현재 발생 사실로 단정하지 않는다.

**개선:** 모델 준비를 제한된 시간 동안 반복 확인하고 실패 원인을 구분한다. worker의 claim·실패 기록 경로를 포함해 지수 backoff·jitter·종료 신호 처리를 설계한다. 회복 가능한 장애와 잘못된 설정을 구분해 재시작 정책을 맞춘다. 인덱싱 지연·마지막 처리 시각을 관측한다.

**완료 기준:** staging에서 긴 모델 준비, 짧은 DB 중단, claim/fail RPC 오류를 주입한 뒤 수동 조작 없이 정상 처리로 복귀하는지 확인한다. 무한 재시작만 만들지 말고 지속 장애는 알림으로 연결한다.

### O06. Python 의존성과 운영 검증의 재현성 보강 필요 — P2 [코드 확인]

**근거:** `services/rag-api/pyproject.toml`은 FastAPI·httpx·pydantic-settings 등의 넓은 버전 범위를 허용하며 전체 해석 결과를 고정한 lockfile은 없다. CI와 운영 문서가 각각 pip 설치를 실행한다. 기존 운영 문서에는 CPU PyTorch wheel·모델 revision·백업·복구 기준이 있으므로 “운영 계획이 없다”는 평가는 맞지 않는다.

**영향:** 같은 소스 커밋이라도 설치 시점에 의존성이 달라질 수 있다. 모델 파일만 고정해도 API·테스트·임베딩 주변 동작은 달라질 수 있다. 문서에 적힌 백업·알림 계획과 실제 수행 결과도 구분해야 한다.

**개선:** CPU/ARM64 운영 환경과 테스트 환경에 맞는 lock 또는 constraints와 해시·업데이트 절차를 마련한다. 배포 결과에는 소스 SHA, 의존성 버전, 모델·임베딩·프롬프트 revision, migration 상태, smoke 결과를 연결한다. 백업 복구·알림 전달은 최근 성공 시각과 증거를 운영 기록으로 유지한다.

**완료 기준:** 동일한 배포 입력으로 환경을 다시 만들 수 있어야 한다. 정상 복구 연습과 알림 테스트의 결과를 확인할 수 있어야 하며, 이번 감사에서 실제 수행 여부를 확인하지 않은 사항은 “운영 미검증”으로 남긴다.

### O07. 출처 형식·키워드 검사만으로 답변의 사실성을 보증하기 어려움 — P2 [코드 확인·평가 설계 제안]

**근거:** `services/rag-api/evaluation/evaluator.py:145–193`은 URL pattern, 답변 용어 포함, 금지 문자열, 거절 marker 등을 판정한다. `sourceUrlValidity`는 안전한 경로 형식과 type 일치 검사이며 실제 공개 URL의 200 응답이나 문장과 근거의 의미 일치를 확인하는 이름은 아니다. 이번 블로그 404처럼 문법상 올바른 출처가 열리지 않을 수도 있다.

**영향:** 필요한 단어와 출처를 넣었지만 사실이 다른 답변도 통과할 여지가 있다. 숫자·수상·기여 범위의 과장, 문장별 잘못된 출처, 불완전한 답변을 놓칠 수 있다. 실제 모델의 그런 답변을 관찰했다는 뜻은 아니다.

**개선:** 구조적 검사와 의미적 평가를 분리한다. 검증된 정답 사실·허용 표현·금지 추론을 case에 정의하고 주요 답변은 사람이 근거와 대조해 평가한다. 인용 ID가 실제 sources에 존재하는지, 공개 대상이 실제로 열리는지 검사한다. 사용자 질문을 무분별하게 저장하지 않으면서 유용성·잘못된 출처 신고를 받을 방법도 검토한다.

**완료 기준:** 출처는 맞지만 주장 수치가 틀린 답변, 없는 S번호, 삭제된 글 URL, 근거 없는 경력·약속이 포함된 반례를 잡아야 한다. 실제 모델을 켠 평가 결과는 O03의 집계 로직 수정 후 별도로 남긴다.

## 8. 권장 진행 순서와 수락 기준

### 1차: 기능과 데이터 신뢰성 복구

E01·E02를 먼저 처리한다. 같은 작업에서 O01·O02의 회귀 검사를 추가해 발행 콘텐츠가 홈·목록·상세·RSS·사이트맵에 일관되게 나타나는지 확인한다. 이어 E03·E04의 폼 상태를 수정하고 실제 staging 계정으로 저장 실패·즉시 발행 후 재저장을 검증한다. 모델 변경·재활성화 전에는 O03의 판정 로직을 보완한다.

**수락:** 공개 데이터가 사라진 것처럼 보이는 결함이 없고, 저장 실패가 입력 손실로 이어지지 않으며, 실패한 품질 검사가 최종 통과로 바뀌지 않는다.

### 2차: 접근성과 주요 사용자 동선 정리

E05를 먼저 정리한 뒤 D09의 색 대비를 수정한다. U02·U08·U09·U03·U04·U05를 중심으로 좁은 화면, 키보드, 카드 이동, 오류 화면을 정리한다. U07의 문의 경로와 U12의 모바일 관리자 로그아웃을 보완한다.

**수락:** 320px에서 핵심 조작이 잘리지 않고, 챗봇이 안내한 목적지를 가리지 않으며, 대표 행동을 키보드와 터치로 사용할 수 있다. 실제 스크린리더 검증은 별도 수행 기록을 남긴다.

### 3차: 평가할 수 있는 콘텐츠로 전환

D01–D07을 적용해 홈의 큰 인사말을 구체적인 역할 설명으로 바꾸고 대표 사례를 앞당긴다. 공개 가능한 실제 산출물과 증빙을 준비한 뒤 E07의 링크 관리 기능으로 연결한다. 소개와 블로그의 내용도 사례·결과 중심으로 보강한다.

**수락:** 대표 사례마다 개인 기여·설계 이유·검증 근거·한계가 있으며, 처음 방문한 사람이 적합한 협업 상대인지 판단할 수 있다.

### 4차: 확장·성능·운영 품질 고도화

E09·E10·E12–E18, O04–O07을 콘텐츠 규모와 운영 필요에 따라 적용한다. 성능 최적화는 실제 측정에서 큰 비용부터 다루고, 보안 강화는 기존 정상 동작과 캐시·렌더링 구조를 함께 검증한다. 백업·복구·알림은 문서뿐 아니라 실행 증거를 남긴다.

**수락:** 콘텐츠가 늘어도 조회·편집 비용과 운영 상태를 설명할 수 있고, 같은 입력으로 배포·평가 결과를 재현할 수 있다.

## 9. 이미 구현되어 있어 유지해야 하는 부분

다음은 현재 코드에서 확인한 기반 기능이다. 새 개선 작업에서 “없는 기능”으로 오인해 중복 구현하거나 제거하면 안 된다.

- 본문 skip link, 공개 main의 포커스 이동, 메뉴 `aria-current`, 모바일 메뉴 Escape와 포커스 복귀.
- 첫 화면 테마 초기화, OS 테마 변경 반영, 명시적 테마 저장과 다른 탭의 storage 변경 반영.
- Markdown 미리보기·이미지 삽입·본문 임시 저장, h2가 충분한 글의 목차, 이전/다음 글과 연관 콘텐츠.
- 관리자 액션의 권한 검사, 서버 입력 검증, 원자 저장·상태 전이 RPC, 편집 버전 충돌 검사.
- 이미지 파일 시그니처·decode·크기 검사, Sharp 재인코딩, metadata 저장, 사용 중 미디어 삭제 방지와 삭제 outbox.
- 공개 콘텐츠 필터와 RLS 관련 SQL, 관리자 noindex, 메타데이터·JSON-LD·RSS·사이트맵 구현 자체.
- 챗봇 SSE 파싱·입력 제한·취소·재시도·서명·rate limit·출처 URL 제한, worker의 revision 기반 원자 활성화.
- Sentry 초기화, liveness/readiness, CI, 운영 runbook, 배포·롤백·백업 가이드.

이 기반이 있다는 사실과 모든 사용 조건에서 완성되었다는 판단은 다르다. 본문 개선사항은 각 기반의 남은 빈틈과 실제 사용에서 발견된 문제를 대상으로 한다.
