## 2. 우선 처리해야 하는 미해결 문제

### V01. 발행 실패 응답에도 폼 상태를 published로 바꿈 — P1 / E03·E04

**확인 위치:** [PostForm](/home/ubuntu/portfolio/src/components/admin/post-form.tsx:65), [PortfolioForm](/home/ubuntu/portfolio/src/components/admin/portfolio-form.tsx:73).

두 폼 모두 성공과 오류를 함께 처리하는 effect에서 마지막 버튼이 `publish`이면 성공 여부를 확인하기 전에 `status: "published"`를 설정한다. 따라서 초안의 “즉시 발행”이 중복 slug 등으로 실패해도 화면은 “발행”으로 바뀐다.

실제 두 컴포넌트에 `{ error: ... }`를 반환하는 저장 함수를 연결하여 확인했다. 오류 안내 후 안정된 화면 상태에서도 기대값 `draft` 대신 `published`가 남았다. 일반 저장 실패의 제목·요약 보존은 개선됐지만 **발행 실패 때의 상태 보존은 충족하지 못한다.** 다음 일반 저장이 잘못된 상태를 제출할 수 있다.

**필요한 수정:** 성공 응답일 때만 서버가 확정한 상태를 반영하고, 오류에는 제출 전 편집 상태를 유지한다. 서버 반환값에 저장된 status를 포함해 버튼의 마지막 의도로 추정하지 않도록 한다. 초안·비공개/숨김에서 발행 실패 → 오류 수정 → 일반 저장의 상태를 각각 검증한다.

근거: [추가 회귀 검사 결과](evidence/2026-09-21/form-verification.txt), [검사 원문](evidence/2026-09-21/form-verification.test.ts.txt). 실제 DB 쓰기는 실행하지 않았다.

### V02. 신규 저장 성공 뒤 다음 저장이 실패하면 문서 식별자와 버전을 잃음 — P1 / E04·E06

**확인 위치:** [PostForm hidden 필드](/home/ubuntu/portfolio/src/components/admin/post-form.tsx:80), [PortfolioForm hidden 필드](/home/ubuntu/portfolio/src/components/admin/portfolio-form.tsx:88).

저장 대상 ID와 버전을 `state.contentId ?? props.id`, `state.updatedAt ?? props.updated_at`에서 매번 가져온다. 신규 편집 화면에는 props의 ID가 없다. 첫 저장 성공이 반환한 ID가 들어갔다가, 두 번째 응답이 `{ error: ... }`이면 직전 성공 정보를 잃어 ID가 빈 문자열로 바뀐다.

신규 글·신규 프로젝트 각각에서 **첫 저장 성공 → 두 번째 저장 실패**를 재현했고, 성공 후 존재하던 hidden ID가 모두 `""`로 변했다. 이후 저장은 기존 항목 수정 대신 신규 생성으로 해석되어 중복 slug 오류 또는 다른 slug의 중복 생성으로 이어질 수 있다. 실제 중복 데이터 생성까지 실행한 것은 아니다. draftKey도 저장된 ID에서 `new`로 돌아갈 수 있다.

**필요한 수정:** 마지막 성공의 문서 ID·버전을 오류 메시지 state와 분리해 유지한다. 신규 저장 성공 후 정식 편집 URL로 전환하고, 오류 응답이 저장 대상을 바꾸지 않도록 한다. 성공 → 실패 → 재시도 흐름을 회귀 검사에 추가한다.

근거: [같은 추가 회귀 검사](evidence/2026-09-21/form-verification.txt). V01·V02를 두 폼에 적용한 총 4개 기대 조건이 모두 실패하여 문제를 재현했다.

### V03. 새 오류 전파 정책과 CI 환경 설정이 맞지 않아 빌드 실패 — P1 / E02·O02

**확인 위치:** [CI 환경과 빌드 단계](/home/ubuntu/portfolio/.github/workflows/quality.yml:19), [명시적 데모 모드와 설정 검사](/home/ubuntu/portfolio/src/lib/content/repository.ts:74).

현재 CI는 Supabase URL·공개 키를 설정하지 않는다. 새 repository는 이 값이 없으면 오류를 던지고, 데모 모드는 `NODE_ENV !== "production"`에서만 허용한다. 따라서 로컬 `.env.local`이 있는 빌드와 깨끗한 CI 빌드의 조건이 달라졌다.

환경 파일이 없는 별도 소스 복사본에서 CI의 공개 설정을 적용하고 빌드했다. 컴파일·타입 검사는 통과했으나 페이지 데이터 수집에서 다음 오류로 종료됐다.

```text
ContentRepositoryError: 공개 콘텐츠를 불러오지 못했습니다: post-list
cause: Supabase public content configuration is missing
Failed to collect page data for /blog/[slug]
```

**필요한 수정:** CI에서 재현 가능한 테스트 DB/fixture와 공개 읽기 설정을 제공하거나, 명시적인 빌드용 fixture 경계를 설계한다. 오류를 다시 빈 배열로 숨기는 방식으로 해결하지 않는다. CI의 `pnpm dev` 기반 E2E를 프로덕션 빌드 대상 검사로 확장하는 기존 계획도 아직 남아 있다.

근거: [격리 환경 빌드 결과](evidence/2026-09-21/ci-build.txt). 이 재현은 현재 Node 환경과 webpack을 사용했으며 GitHub Actions 실행 자체를 확인한 것은 아니다. 첫 복사본의 scripts 누락에 따른 타입 오류는 복사 범위를 보완한 뒤 재검사했고, 위 결과는 이를 해결한 최종 실행이다. 원본 작업 공간의 기본 `pnpm build`는 통과했다.

전역 reset을 base layer로 옮긴 수정은 확인했다. 그러나 새 `solid-primary-cta`가 일부 링크에만 적용되고, 실제 “문의하기”는 여전히 밝은 primary 배경에 흰 글씨를 쓴다. `ProjectVisual`의 blue 배경과 기간·유형 글씨, 상단 “협업 문의”, 라이트 푸터도 부족하다.

배포된 사이트의 7개 공개 경로를 라이트·다크 두 테마로 검사한 **14개 조합 모두에서 텍스트 대비 문제가 남았다.** 같은 공통 header/footer가 여러 경로에 반복 검출된 것이므로 14개의 독립 결함이라는 의미는 아니다.

| 실제 요소 | 테마 | 측정 대비 | 일반 텍스트 목표 |
| --- | --- | ---: | ---: |
| 상단 “협업 문의” | 양쪽 | 3.80:1 | 4.5:1 |

**필요한 수정:** 컴포넌트별 실제 배경과 전경을 함께 수정하고 normal·hover·focus 상태를 두 테마에서 검사한다. 현재 E2E 파일명에 accessibility가 있어도 색 대비 검사를 실행하는 것은 아니다.

근거: [배포 사이트 접근성 결과](evidence/2026-09-21/live-accessibility.json), [다크 상세 화면](screenshots/2026-09-21/live-project-dark.png), [문의 CTA 코드](/home/ubuntu/portfolio/src/components/content-discovery.tsx:56).

### V06. 한글 조합 종료 때 최종 검색값이 URL에 저장되지 않는 경로 — P2 / U01

**확인 위치:** [검색 effect](/home/ubuntu/portfolio/src/components/blog-browser.tsx:38), [입력 이벤트 처리](/home/ubuntu/portfolio/src/components/blog-browser.tsx:69).

로컬 state와 180ms debounce로 빠른 영문 입력은 개선됐다. 다만 조합 여부는 ref에만 있다. 조합 중 최종 문자열이 이미 state에 들어간 뒤 `compositionend`가 같은 값으로 `setQuery()`를 호출하면 effect를 다시 실행할 변경이 없다.

배포 브라우저에서 `compositionstart → input("한") → compositionend("한")` 순서의 합성 이벤트를 보내고 700ms 기다렸다. 입력값은 “한”인데 URL은 `/blog` 그대로였다. 화면의 로컬 필터는 움직여도 새로고침·공유에 검색 조건이 남지 않을 수 있다. **실제 OS 한글 입력기를 조작한 검사는 아니며, 특정 이벤트 순서의 경계 사례를 재현한 것이다.** 기존 테스트는 compositionend 뒤 문자열을 추가로 바꿔 이 경로를 놓친다.

**필요한 수정:** 조합 종료를 URL 갱신의 명시적인 트리거로 처리하고, 조합 전 예약된 debounce도 취소한다. 최종 입력값이 compositionend 이전에 이미 반영되는 경우와 이후에 반영되는 경우를 모두 검사한다.

근거: [합성 이벤트 결과](evidence/2026-09-21/ime-reproduction.json), [기존 IME 검사](/home/ubuntu/portfolio/src/components/blog-browser.test.ts:75).

### V08. 시스템 테마 복귀와 초안의 계정·작성 세션 구분이 아직 없음 — P2~P3 / U13·E06

모션 감소 CSS와 메타데이터까지 포함한 draft는 개선됐다. 그러나 다음 두 수락 조건은 아직 구현되지 않았다.

- [ThemeToggle](/home/ubuntu/portfolio/src/components/theme-toggle.tsx:54)은 light/dark만 번갈아 저장한다. 처음 OS 설정을 따르는 동작은 있지만 명시적으로 고른 뒤 **system으로 돌아가는 UI가 없다.** 기존 E2E는 저장소 값을 직접 지워 초기 상태로 돌리므로 사용자 복귀 동선을 검증하지 않는다.
- [초안 storageKey](/home/ubuntu/portfolio/src/components/markdown-editor.tsx:110)는 `portfolio-cms-draft:post:new`, `portfolio-cms-draft:portfolio:new` 같은 공통 신규 키를 계속 사용하며 계정·작성 세션 식별이 없다. 잘못된 초안을 자동 적용한 사고를 확인한 것은 아니지만, 계정 전환·동시 신규 문서의 분리라는 원래 완료 조건은 충족하지 못한다.

### V09. 자동 검사 통과 기록을 그대로 재사용할 수 없음 — P2 / O02

현재 전체 Vitest 실행은 **169개 중 168개 통과·1개 실패**였다. 실패는 PostForm 발행 성공 뒤 select가 `published`여야 한다는 기존 검사로, 실제 관찰값은 `draft`였다. 같은 파일만 다시 실행하면 4개 모두 통과했다. 따라서 항상 실패하는 기능으로 단정하지 않되, **실행 타이밍에 따른 불안정성은 남아 있다.** 성공 안내와 상태 동기화의 순서 및 테스트의 대기 조건을 함께 확인해야 한다.

또한 현재 CI는 챗봇 E2E를 제외하고 개발 서버를 검사한다. 이번에 발견한 발행 실패·연속 저장 ID 보존·실제 색 대비 검사도 없다. 검사 개수가 늘었다는 사실과 계획한 품질 게이트가 완성됐다는 판단은 구분해야 한다.

근거: [최초 전체 검사](evidence/2026-09-21/vitest.txt), [실패 파일 재실행](evidence/2026-09-21/forms-rerun.txt).

## 3. 실제로 개선된 부분

### 공개 콘텐츠 조회와 공유 정보

공개 권한의 Supabase 관계 조회는 HTTP 200으로 발행 글 3개를 반환했다. 배포된 홈·블로그 목록 모두 같은 글 3개가 보이고, 글 상세 3개가 모두 HTTP 200이다. RSS의 item도 3개, 사이트맵의 글 상세 URL도 같은 3개다. 대표 이미지가 없는 글의 OG는 기본 `/og.png`로 생성된다.

이전의 **블로그 0개·상세 404 문제는 현재 공개 데이터에서 해결된 것으로 확인했다.** 다만 현재 글에는 대표·본문 이미지가 없어 “대표 이미지 있음/본문 이미지 있음”까지 실제 테스트 DB fixture로 확인한 것은 아니다. 따라서 E01 전체 수락 범위는 부분 반영으로 기록한다.

근거: [공개 데이터 조회](evidence/2026-09-21/public-data.json), [공개 집합 일치 검사](evidence/2026-09-21/content-consistency.json).

### 모바일·탐색·챗봇

- 320px에서 블로그 입력창은 x=76px, 폭=194px로 오른쪽 끝이 270px에 머물렀다. 이전 잘림은 재현되지 않았다.
- 소개·포트폴리오·블로그에 대표 h1이 있고, 직접 없는 경로와 없는 글의 404는 각각 main이 하나다. 다만 목록 카드가 h1 다음 h3로 건너뛰는 best-practice 경고는 남는다.
- 현재 메뉴의 시각적 표시와 `aria-current`가 연결되어 있다.
- 챗봇 확인 중에도 닫기 버튼에 포커스가 들어왔다. “소개 보기” 이동 후 dialog가 0개가 되고 모바일 scroll lock이 해제됐으며 main으로 포커스가 이동했다.
- 긴 대화 스크롤, 기록 지우기, 상태 조회 timeout, 부분 답변·취소 구분의 관련 컴포넌트 검사는 통과했다. 이는 모킹 기반 결과이며 실제 모델 응답 품질의 증거는 아니다.

### 오류 처리·미디어·평가 로직

- repository가 조회 실패를 `[]`/`undefined`/demoProfile로 조용히 바꾸는 흐름은 제거됐다. 블로그 오류 UI와 재시도 조작도 생겼다. 단, 전 공개 화면의 오류·복구 정책과 timeout 검증은 남는다.
- reset이 `@layer base`로 이동했고 선택 필터에 선언한 흰 글씨가 적용된다. 전역 계층 문제와 개별 색 대비 문제는 구분해서 평가했다.
- CMS의 일반 저장 오류 후 제목·요약·대표 이미지 보존, 전체 필드 draft, 이미지 크기 metadata와 장식용 빈 alt 지원이 추가됐다. 발행 실패와 연속 저장 문제는 V01·V02에 별도로 기록했다.
- RAG gate는 전체·그룹 성공률, 답변 용어, 지연, case 누락·중복을 판정에 포함하도록 보강됐다. Python 검사 56개가 통과했다. 실제 모델 평가는 수행하지 않았다.

## 4. 디자인·콘텐츠의 변화와 남은 일

대표 프로젝트가 작업 원칙보다 먼저 나오도록 순서는 바뀌었다. 390×844 화면에서 대표 섹션 제목은 약 **1,026px**, 첫 프로젝트 제목은 약 **1,501px**에 위치했다. 이전 약 1,936px·2,410px보다 앞당겨졌지만 한 번의 짧은 스크롤로 사례의 제목·의미를 보는 목표는 추가 조정이 필요하다.

그 외 중요한 콘텐츠는 현재도 동일하다.

- 홈의 큰 제목은 “안녕하세요.”, 본문은 “송경근입니다.”다. 해결하는 문제·전문성을 중심으로 바꾸는 D01은 아직 반영되지 않았다.
- 프로젝트 4건 모두 연결된 증빙 링크 0개, 미디어 0개다. 실제 결과물 대신 비슷한 placeholder가 표시된다.
- 프로젝트 본문은 현재 98~237자의 짧은 내용이다. 대표 사례 2건의 역할·선택·검증·한계 템플릿이 적용되지 않았다.
- 글 3개 본문은 각각 140·134·120자로 이전과 같다. 내용이 짧다는 이유만으로 나쁜 글이라고 판단한 것이 아니라, 원 계획의 실제 경험·적용 사례 보강이 일어나지 않았음을 확인한 것이다.
- 히어로의 잘리는 확대는 `object-contain`으로 완화했고 “Live”는 “업무 흐름 예시”로 바뀌었다. 다만 `/og.png` 재사용과 겹치는 장식 패널은 유지된다.
- 소개 페이지에는 여전히 경력 기간·역할·프로젝트 연결·외부 증빙의 확장이 없다. 카드의 기간·유형도 시각 영역과 본문에서 반복된다.

사용자 자료가 필요한 사실·성과를 임의로 만들지 않은 것은 적절하다. 다만 이 항목들은 “구현됐으나 승인만 남음”보다 **콘텐츠 준비 및 구현 미완료**로 설명하는 편이 정확하다.

## 7. 후속 작업 순서

1. **CMS 상태와 저장 대상 유지:** V01·V02를 먼저 수정하고 신규·기존 항목의 성공/실패/재시도 전체 흐름을 고정한다. V09의 성공 검사 불안정성도 함께 해결한다.
2. **CI가 같은 조건을 검증하도록 정리:** 설정/fixture를 제공해 V03을 해결하고 프로덕션 서버·챗봇 모킹·실제 대비 검사를 배포 기준에 포함한다.
3. **공개 사용성 마무리:** V04~V08의 대비·이동 문구·IME·메일 절대 URL·system 테마 복귀를 처리한다. 부분 반영 항목을 자동으로 완료 처리하지 않는다.
4. **콘텐츠 준비와 구현을 분리해 진행:** 대표 사례 2건·글 1건·공개 가능 산출물을 확보한 뒤 D01~D07과 CMS 링크 편집을 완성한다. 사실 자료가 필요 없는 CMS 링크 UI·테마·CI 작업까지 같이 보류할 필요는 없다.
5. **운영·확장 과제는 별도 검증 기록으로 마감:** 데이터 규모·성능 기준·CSP 관측·복구·RAG 의미 평가의 실행 증거를 남긴다.

이번 작업은 반영 여부 검증과 문서·근거 저장만 수행했다. 기존 구현 파일과 진행 현황 문서는 수정하지 않았다.
